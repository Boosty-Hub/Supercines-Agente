# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es

Template para construir un **agente conversacional sobre Kommo CRM** con clasificación, respuesta vía Anthropic Managed Agent (+ Memory Stores) — todo sobre **Haiku 5.5** (`claude-haiku-5-5`) por defecto, aprendizaje automático nocturno (Dreams) y evaluación de calidad (Outcomes). Se customiza para cualquier operador **desde el dashboard** (`/setup` + `/agent`), sin tocar código.

Repo: `web/` (Next.js 15 (React 19) dashboard + API routes) + `supabase/` (Postgres migrations + Edge Functions Deno) + `agent/` (template de system prompt).

## Desplegar un cliente nuevo (zero-CLI — todo desde el navegador)

El flujo es **single-tenant**: un clon = un cliente. Cada cliente tiene su propio Supabase, su propia conexión Kommo y su propia cuenta/API key de Anthropic. La personalización por cliente vive en la tabla `runtime_config` (DB), editable desde el dashboard — NO se edita código.

1. **Crear infra externa** (manual, irreducible): un proyecto Supabase nuevo, una API key de Anthropic, una integración long-lived token en Kommo.
2. **Deployar en Netlify/Vercel** (import from Git, una vez): en **Netlify es zero-config** — `netlify.toml` ya fija `base = "web"`, `command = "pnpm build"`, `publish = ".next"`, Node 22, `PNPM_VERSION` y `@netlify/plugin-nextjs`. En Vercel: root directory = `web/`, build `pnpm build`, env `ENABLE_EXPERIMENTAL_COREPACK=1` (respeta `packageManager` de `web/package.json`, pnpm 10.32.1: un pnpm viejo falla con `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` por los `overrides` del lockfile) y Node 22. `PNPM_VERSION` (netlify.toml) y `packageManager` deben coincidir; los scripts de build permitidos y los advisories aceptados viven SOLO en `web/pnpm-workspace.yaml`. El host hace checkout del repo **completo** (no solo `web/`) para que el codegen lea `../supabase/` en el build. El **primer deploy FALLA** hasta cargar las env vars — es esperado.
3. **Configurar las 3 variables en el host** (Netlify: Site configuration → Environment variables · Vercel: Project Settings → Environment Variables), luego **redesplegar**. Las tres salen del proyecto Supabase nuevo en **Project Settings → API**. ⚠️ Usar las keys **LEGACY JWT** (empiezan con `eyJ`), NO las nuevas `sb_publishable_`/`sb_secret_` (PostgREST rechaza las nuevas):
   - `NEXT_PUBLIC_SUPABASE_URL` — Project URL (`https://<ref>.supabase.co`)
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` — Legacy API keys → `anon (public)`
   - `SUPABASE_SERVICE_ROLE_KEY` — Legacy API keys → `service_role (secret)`
4. **Abrir la URL** → el wizard `/first-run` detecta el estado y guía el siguiente paso.
5. **Wizard `/first-run`**: paso Conectar (ya hecho) → paso Inicializar (pegás un Personal Access Token `sbp_...` de `supabase.com/dashboard/account/tokens`; el wizard aplica las migraciones + deploya las Edge Functions con progreso en vivo) → paso Crear usuario (email + contraseña; el maestro nace con `app_metadata.role = "configuracion"` explícito y, con el token `sbp_` del paso anterior, el wizard cierra el registro público de Supabase Auth —`disable_signup: true` vía Management API— y lo verifica; si falla muestra el paso manual y `health-scan` abre el incidente `registro_abierto`). Al terminar, entrás **directo al dashboard** (`/inbox`). **Acá el onboarding crea/provisiona todo el proyecto solo.**
6. **Wizard de provisioning (panel lateral, NO bloqueante)**: Anthropic credentials + Managed Agent + Verticales (opcional) + Memory Stores + Kommo. Vive como un drawer derecho SOBRE el dashboard (`web/src/app/(dashboard)/setup-drawer.tsx`), se auto-abre 1x por sesión si falta config, se puede cerrar/reabrir (botón flotante o `/setup`, que redirige a `/inbox?setup=open`). Idempotente. Estado computado en `web/src/lib/setup-state.ts` (DB-only).
7. **`/agent`**: editás voz/identidad/branding cuando quieras; al guardar sincroniza el system prompt con Anthropic (sube versión).

> **Guía paso-a-paso completa** (para humanos, con cada wizard detallado): `README.md` (Pasos 1-7) y `SETUP-WITH-CLAUDE.md` (Fase 4 deploy Netlify/Vercel · Fase 5 env vars + `/first-run`). Mantené estas tres en sync si cambia el flujo.

### Codegen automático

`pnpm dev` y `pnpm build` corren automáticamente `node scripts/embed-provision.mjs` (hooks `predev`/`prebuild`). El script embebe todas las migraciones SQL y el source de las 8 Edge Functions en archivos TypeScript generados (`web/src/lib/provision/*.generated.ts`, gitignoreados). Esto permite que el wizard `/first-run` aplique migraciones y despliegue funciones sin acceso al filesystem en runtime. **Si el directorio `../supabase/` no existe, el build falla intencionalmente** — diseñado para que el build no pase en silencio con un provisioner vacío.

### Precedencia de config (clave)

> **Excepción — secretos atados a un destino** (`KOMMO_ACCESS_TOKEN`, `SHOPIFY_ACCESS_TOKEN/CLIENT_ID/CLIENT_SECRET`, `BCV_RATE_APIKEY`, `TOOL_<X>`): viven SOLO en `runtime_config`, SIN fallback al entorno (ni `process.env` de la web ni `Deno.env` de las Edge: `lib/db-only-secret-keys.ts`, copia en `_shared/db-only-secret-keys.ts`). La validación que obliga a reenviar el secreto al cambiar su destino (`secret-bound-config.ts`) decide sobre lo único que puede viajar; si el secreto pudiera vivir también en un entorno distinto del que mira esa validación, seguiría vigente y viajaría al host nuevo. El wizard `/setup` ya escribe estas claves en la base. **Al portar:** un cliente con alguno de estos secretos solo como variable de entorno/secret de Supabase debe cargarlo en `runtime_config` (desde `/setup` o `/config/kommo`) antes de actualizar.

`runtime_config` es la **single source of truth**. Web y Edge Functions resuelven cada key **DB-first / env-fallback**: si la fila existe y `value` no es NULL ni `""` → se usa; si no → variable de entorno; si no → undefined. Los lectores: `web/src/lib/runtime-config.ts` (React `cache()` por request) y `supabase/functions/_shared/config.ts` (cache TTL 60s, lectura en runtime). Tras escribir config desde el dashboard, las Edge Functions la toman dentro de 60s sin redeploy.

```bash
# Front (desde web/)
cd web && pnpm install
pnpm dev            # dev server :3000; corre codegen automáticamente al arrancar
pnpm build
npx tsc --noEmit    # typecheck — correr SIEMPRE tras editar el front (no hay test suite)

# Re-deploy de una Edge Function puntual
SUPABASE_ACCESS_TOKEN=<token> npx supabase functions deploy <fn> --project-ref <ref> --no-verify-jwt
# ...y SIEMPRE después (commiteado y pusheado): registrar la huella que compara el panel
SUPABASE_ACCESS_TOKEN=<token> node web/scripts/record-function-hashes.mjs --project-ref <ref> --site https://supercines.netlify.app
```

> **Huella de un deploy por CLI** (`web/scripts/record-function-hashes.mjs`, del template): el panel (`/api/provision/status`) decide «al día» comparando el `hash` de cada bundle embebido en la web contra `runtime_config.DEPLOYED_FUNCTION_HASHES`. El wizard lo registra al desplegar; `supabase functions deploy` no. Sin el registro el panel ve todas las funciones «faltantes» (count 0) y ofrece redesplegarlas — con una web vieja publicada, eso las revierte. El script baja lo desplegado (`supabase functions download --use-api`), lo compara byte a byte con el repo, exige `verify_jwt=false` y solo entonces registra (fusiona) la huella; con `--site` confirma que la web publicada embebe el mismo código (count = total). La huella sale de `scripts/lib/function-bundles.mjs`, el MISMO módulo del codegen (test `scripts/function-bundles.test.mjs`; en SuperCines el bundle excluye los `*.test.ts` de `_shared/`). Cualquier cambio en `_shared/` cambia la huella de las 13 funciones: correr el script sobre TODAS; las que no importan lo cambiado siguen idénticas al repo y registran sin redeploy, las que corren código distinto quedan «NO» y hay que desplegarlas.

> **Sincronizar el scaffold del agente de un cliente por CLI** (`web/scripts/sync-agent.mjs`): el equivalente del botón «Sincronizar» (/agent, /consumo) para mantener una flota. **Cuándo correrlo**: tras un deploy que cambia `CORE_SCAFFOLD` o las tools/instrucciones del agente (el banner «agente desactualizado» lo delata: `AGENT_SCAFFOLD_HASH` ≠ huella del código). Uso: `SRK_CLIENTE=<service_role> node web/scripts/sync-agent.mjs --supabase-url https://<ref>.supabase.co --service-role-key-env SRK_CLIENTE [--dry-run] [--sync-model] [--resolve overwrite|import_live --expected-live-hash <liveHash>]` (la clave solo por el NOMBRE de una variable de entorno, nunca por argv, jamás se imprime; la config sale de `runtime_config` por la base, sin fallback al entorno local). **Garantías**: no reimplementa nada, importa los mismos módulos que la web (`lib/agent-sync-core.ts` compone el system con `composeSystem` + `CORE_SCAFFOLD` + `renderToolsList` y decide con `guardedPush`/`detectPromptConflict`; `anthropic-managed.ts`; por eso esos archivos deben seguir siendo importables por Node con type-stripping: imports relativos `.ts`, sin `@/`, sin parameter properties/enums). Ante `prompt_changed` / `version_ahead` / `first_sync_differs` ABORTA (exit 2) mostrando alcance (operator/scaffold), el diff y el `liveHash`; resolver exige `--resolve` + ese `--expected-live-hash` (si el vivo cambió, exit 3 y no hace nada). Escribe solo `ANTHROPIC_AGENT_VERSION`, `AGENT_SCAFFOLD_HASH` y `AGENT_PROMPT_SYNCED_HASH`; **nunca `SYSTEM_PROMPT`**, salvo `--resolve import_live` (importar lo vivo, igual que el botón). `--dry-run` solo lee: imprime hashes, alcance, resumen del diff, deriva de modelo y qué haría. `--sync-model` alinea además el modelo vivo con `AGENT_MODEL` (`agentModelParam`, `{id, effort}`). Tests: `web/scripts/sync-agent.test.mjs` (Supabase y Anthropic falsos).

> No hay `pnpm bootstrap`, `pnpm migrate` ni `pnpm user:master`. Esos scripts fueron eliminados. Todo sucede desde el browser vía `/first-run`. Para desarrollo local, el codegen corre automáticamente en `predev`.

No hay linter más allá de `eslint-config-next`. Verificación de cada cambio del front: `npx tsc --noEmit`.

Las Edge Functions **sí** se pueden typechequear y testear localmente aunque Deno no esté instalado:

```bash
npx deno@2 check --node-modules-dir=auto supabase/functions/*/index.ts supabase/functions/_shared/*.ts
npx deno@2 test  --allow-net --allow-read --allow-env --node-modules-dir=auto supabase/tests supabase/functions/_shared/
```

Hacelo SIEMPRE antes de deployar: el deploy no typechequea, así que un error de tipos llega a producción en silencio.

⚠️ `npx tsc --noEmit` NO sustituye a `pnpm build`. Next valida reglas propias que `tsc` no ve — por ejemplo, un `route.ts` **no puede exportar nada que no sea un handler** (`export function parseTerms` → `"parseTerms" is not a valid Route export field`, con `tsc` en verde). Los helpers compartidos entre rutas van en `src/lib/`, nunca exportados desde un `route.ts`.

Incluye `supabase/tests/web-parity.test.ts` (paridad web↔Edge de pricing, modelos y alcances) y `dashboard-ai-body.test.ts`, que captura el body HTTP real del AI SDK (baja `ai`/`@ai-sdk/anthropic` de npm la primera vez) y afirma que no viaje `temperature`/`top_p`/`top_k`, que Haiku 5.5 rechaza con 400.

## Arquitectura — el pipeline (lo más importante)

Mensaje entra a Kommo → llega al sistema y fluye así, **todo desacoplado por la tabla `inbound_queue` + Edge Functions encadenadas**:

```
Kommo webhook ──> kommo-webhook ──> inbound_queue (pending)
                                          │ (waitUntil)
                                          ▼
                   process-inbound: parsea payload, upsert leads, inserta
                   messages, clasifica inbound (CLASSIFY_MODEL, Haiku 5.5) (vertical +
                   intent/urgency/toxicity/requires_human_review) — con
                   contexto de los últimos turnos del lead
                                          │ (waitUntil, modo cola sin message_id)
                                          ▼
                   generate-response: DEBOUNCE 45s por lead → batch de
                   TODOS los mensajes sin responder + [HISTORIAL] determinístico
                   de la DB → sesión CMA (AGENT_MODEL, Haiku 5.5) con Memory Stores → 1 draft
                                          │ (si approved)
                                          ▼
                   publish-to-kommo: PATCH custom field configurado +
                   corre salesbot → evaluate-outcomes (graders)
```

Resiliencia: `pg_cron` barre cada minuto `process-inbound`, `generate-response`, `publish-to-kommo` (migraciones 0006/0007/0013) por si el fire-and-forget se corta. `dreams-run` (daily/weekly) y `evaluate-outcomes`/`alerts-scan` (cada 5 min) también por cron.

### Invariantes críticos (romperlos rompe producción)

1. **`verify_jwt = false` para TODAS las Edge Functions.** Kommo postea sin JWT; con `verify_jwt=true` da 401 y nada entra. En deploys por CLI, está fijado en `supabase/config.toml` bajo `[functions.*]`. En deploys desde el browser (wizard `/first-run`), se fuerza vía la metadata del API call: `{ verify_jwt: false }` en cada llamada a `POST /v1/projects/{ref}/functions/deploy` (ver `web/src/lib/provision/management.ts`). **Nunca quitar ninguno de los dos mecanismos.** `verify_jwt=false` NO significa «sin autenticación»: **todas las funciones salvo `kommo-webhook` exigen el header `x-internal-secret`** (`_shared/auth.ts` → `authorizeInternal`, comparación en tiempo constante, 401 genérico, fail-closed). El secreto es `INTERNAL_FUNCTION_SECRET` en la tabla protegida `_app_secrets` (0061: sin policies, sin grants a anon/authenticated; se genera por despliegue, nunca vive en el repo ni en el SQL). Lo mandan: pg_cron (las funciones `trigger_*`, SECURITY DEFINER, leen `internal_function_headers()`; 0069), las funciones entre sí (`callInternal`) y el servidor del panel (`lib/internal-call.ts`; ninguna ruta web lo expone al navegador ni usa la service key como Bearer). `kommo-webhook` es pública porque Kommo no firma sus webhooks ni puede presentar el secreto; sus mitigaciones están en el encabezado de su `index.ts`. **Toda función nueva** debe llamar a `authorizeInternal` (el test `gate-coverage.test.ts` falla si no) y figurar en `DEPLOY_ORDER`. **Orden de despliegue sin downtime** (en SuperCines lo hace el operador con el PAT temporal, ver el runbook del final): migraciones → funciones en `DEPLOY_ORDER` (invocadores antes que invocados: cuando una función empieza a exigir el secreto, quienes la llaman ya lo mandan) → web (si el secreto aún no existe llama sin header y la función vieja responde igual). Una llamada que caiga entre dos despliegues recibe 401 y la repone el barrido de pg_cron.

2. **El trabajo lento del agente va dentro de `EdgeRuntime.waitUntil()`.** `generate-response` crea el draft `pending`, devuelve **202 de inmediato**, y corre el agente (~60-80s) en `waitUntil`. Si se hiciera antes de responder, el runtime mata la función al desconectarse el cliente (pg_net/fire-and-forget) → draft `pending` eterno. Mismo patrón en `kommo-webhook`→`process-inbound` y `process-inbound`→`generate-response`. **`process-inbound` también responde 202 y drena en `waitUntil`** (`drainQueue`: hasta 5 lotes / 60s por invocación) — ver el invariante 6. **`publish-to-kommo` también** (desde 0074): responde 202 `{accepted, run_id}` y publica en `waitUntil`; los conteos quedan en el log, no en la respuesta (ver «Publicación a Kommo» abajo). Regla general para todo destino de un disparo con timeout corto (panel: `triggerInternalFunction` 4 s; pg_net: 20-120 s; `callInternal` entre funciones): **o responde 202 y trabaja en `waitUntil`, o es idempotente ante la muerte a mitad**. Cuando el llamador SÍ necesita el resultado (reintento manual de seguimiento, corrida manual de Dreams) el trabajo se envuelve en `keepAlive()` (`_shared/keep-alive.ts`: `waitUntil` + se espera la misma promesa) para que un corte del llamador no lo deje a medias.

3. **Debounce + batching.** `process-inbound` dispara `generate-response` en **modo cola** (sin `message_id`) para que aplique el debounce. `generate-response` espera 45s de silencio desde el último inbound del lead y responde TODOS sus mensajes pendientes en UN solo draft (resuelve los "3 mensajes cortados = una idea"). `messages.answered_by_draft_id` marca todo el batch como cubierto (FK `on delete set null` → si el draft se borra por stale, se reprocesan). Drafts `pending` con `agent_metadata.generating=true` >8min se consideran runs muertos: un barrido global al inicio del modo cola los borra (el FK libera su batch para reprocesar). El umbral es holgado adrede — runs vivos con muchos tool calls llegan a ~2.5min, y borrar un run vivo solo duplica trabajo (las guardas `status='pending'` en delete/update evitan perder o duplicar respuestas).

4. **Tres switches en `kommo_publish_config` (singleton `is_active=true`):**
   - `agent_enabled` — kill switch; si `false` `generate-response` no genera nada.
   - `publishing_enabled` — si `false`, drafts se generan pero NO se publican (shadow/validación).
   - `bypass_review` — si `true` (y `publishing_enabled=true`), el agente responde y publica TODO aunque entre a review. No afecta el botón de revisión humana (forceReview siempre queda `pending`).
   - Combinación de validación inicial: `agent_enabled=true, publishing_enabled=false`.

5. **`ignored_channels` ≠ "no clasificar" (migración 0052).** Un canal en `ignored_channels` que además esté en `classify_only_channels` SÍ se clasifica y SÍ se rutea al equipo — solo que el agente no le escribe al lead. La marca `ignored` se aplica **después** de clasificar (`generate-response` filtra por `ignored`, así que igual no responde). Si alguna vez tocás el gate de canal de `process-inbound`, el fallback del `select` de `getPublishFilters` es obligatorio: pedir una columna inexistente hace fallar el select entero y `channels` quedaría vacío → **el agente empezaría a responder en canales silenciados**.

6. **El webhook tiene que devolver rápido y NO quedar enganchado al downstream — si no, Kommo lo deshabilita.** Kommo apaga un webhook cuyo endpoint le falla de forma sostenida, y no avisa a nadie: en el deployment de KIA eso dejó el sistema mudo 6 días seguidos (jul 30–ago 4 de 2026) y otros 4 (ago 7–ago 10), con 219 mensajes de clientes que nunca entraron al sistema. La causa era estructural: `kommo-webhook` disparaba **un `process-inbound` por cada webhook** y lo sostenía con `waitUntil` hasta que terminaba el lote entero (MAX_BATCH payloads × clasificador + API de Kommo = minutos), así que el worker del webhook vivía tanto como el downstream; bajo ráfaga (43.989 webhooks en un día) se agota el pool → 5xx → Kommo desconecta. Reglas que **no hay que revertir**:
   - `kommo-webhook` (`_shared/kommo-webhook-handler.ts`) responde **200 de inmediato** tras validaciones baratas (método, tamaño ≤ 1 MB, parseo del cuerpo): **nada que dependa de Postgres/PostgREST está antes de la respuesta**, ni siquiera la autenticación. Decidir con el secreto y encolar corren en `EdgeRuntime.waitUntil`. Un rechazo es un **descarte silencioso** (Kommo recibe 200; nunca un 401 sostenido que lo haga deshabilitar el webhook).
   - `process-inbound` responde **202 al toque** y drena en `waitUntil` (antes hacía todo dentro del request handler).
   - `kommo-webhook` **coalesce** el trigger (máx. 1 cada 2s por instancia) y **solo dispara si el payload es accionable** (`message.add` / `leads.add` / `leads.status`; **en SuperCines `leads.update` solo se encola**, ver abajo). `leads.update` y `leads.status` son ~**64% del tráfico**; desde 0061 `leads.status` SÍ es accionable porque mueve la tarjeta del tablero, pero `process-inbound` solo **escribe si cambió la etapa o el pipeline** (`_shared/lead-position.ts`: la mayoría son de otros campos) y sale antes de cargar verticales/filtros si el payload no trae leads nuevos ni mensajes. El endpoint sigue siendo «insertar y responder»: el coalescing de 2 s acota el costo y el refresco en vivo del inbox se agrupa cada 5 s. `isActionable` es **fail-open**: ante una forma que no sabe inspeccionar, dispara.
   - **SuperCines — volumen de `leads.update`:** los Salesbots escriben custom fields del lead todo el día y cada escritura genera un `leads.update`. Por eso `isActionable` (`_shared/kommo-webhook-handler.ts`) NO dispara `process-inbound` con un `leads.update` (solo `leads.status` / `leads.add` / `message.add`): el payload se encola y lo levanta el barrido de pg_cron cada minuto, que sincroniza la posición igual. El trabajo de fondo por request es «autenticar con el estado en caché + un insert» (el estado se carga a lo sumo una vez por ventana de 30 s y la nota de autenticidad sale una vez por minuto y tipo): `kommo-webhook-handler.test.ts` lo mide con 2000 `leads.update` seguidos (2000 inserts, <= 2 cargas de estado, 0 triggers).
   - `claim_inbound_batch` tiene **reaper**: recupera los `processing` huérfanos de entre 10min y 24h (10min > el wall clock máximo de una Edge Function ⇒ están muertos con certeza) y marca `failed` los de +24h en vez de replayarlos — reprocesar un mensaje viejo le mandaría una respuesta a una conversación fría, porque `messages.created_at` se reescribe a `now()` y la ventana de frescura (`answer_max_age_hours`) ya no lo filtra. Sin el reaper, un worker muerto dejaba la fila invisible **para siempre**.
   - `upsertLead` reintenta ante **23505**: el webhook y el sweep de pg_cron corren en paralelo y el select-then-insert se pisa; el error mataba la fila entera de la cola con TODOS sus mensajes.
   - Red de seguridad: la alerta **`inbound_silence`** (`alerts-scan`) salta con cero webhooks en 90 min de horario laboral. Es lo único que convierte un apagón de días en un aviso.

7. **Migraciones con `${SUPABASE_URL}` placeholder.** Las migraciones que crean cron jobs (0006, 0007, 0009, 0010, 0011, 0013) usan `'${SUPABASE_URL}/functions/v1/<fn>'` en lugar de URLs hardcoded. La sustitución ocurre **en runtime** dentro de `web/src/app/api/provision/migrate/route.ts` antes de ejecutar cada SQL. El placeholder viaja intacto en los archivos `.sql` y en el archivo generado `migrations.generated.ts`. **No reemplazar el placeholder con la URL real en los archivos SQL** — dejá el placeholder para que el repo siga siendo reusable.

### Mensaje sin lead (onlinechat): no se pierde (`_shared/lead-resolver.ts`, migración 0092)

Los `message.add` de `origin: onlinechat` llegan con `chat_id`/`talk_id`/`contact_id` pero **sin `entity_id`/`element_id`**: Kommo crea el lead DESPUÉS de disparar el webhook (Vitalicia, 2026-10-19). Antes `process-inbound` hacía `continue` y el primer mensaje de una conversación nueva desaparecía sin rastro. Ahora:
- **Resolver**: sin id en el payload, `GET /api/v4/talks/{talk_id}` (`kommo.ts` `fetchTalk`, con el mismo reintento ante 429 que el resto) → `entity_id` si `entity_type` es `lead` (o `_embedded.leads[0].id`). Forma desconocida, `entity_type` distinto de lead, `entity_id: null` (Kommo aún no lo creó) o error = **sin resolver**, nunca se adivina. Un talk que dice contacto/empresa es **transitorio** (`talk_other_entity`: mientras Kommo crea el lead el talk puede apuntar todavía al contacto; se reintenta como `talk_not_found`); solo es permanente (`not_lead_entity`) si lo dice el PAYLOAD. Sin `talk_id` (solo chat/contact) no hay a quién preguntar. **Acotado (webhook público, H2/L4)**: por fila de la cola a lo sumo `MAX_TALK_LOOKUPS_PER_ROW` (5) talks DISTINTOS —**1 si la fila llegó sin firma**— (el resto → `talk_lookup_capped`, sin consultar) dentro de `TALK_LOOKUP_ROW_BUDGET_MS` (20 s) y del **plazo de la corrida** `TALK_LOOKUP_RUN_BUDGET_MS` (45 s desde el inicio de `drainQueue`, compartido por TODAS sus filas y lotes: el presupuesto por fila solo no acotaba un lote de muchas filas); la consulta en curso se aborta con `AbortSignal` → `talk_lookup_budget`, transitorio; caché de talks de la corrida (`drainQueue`): positivos siempre, negativos por `NEGATIVE_TALK_CACHE_MS` (4 s < la primera espera de 5 s: un reintento legítimo nunca choca con su propio negativo).
- **Ids del payload**: `entity_id` solo vale si `entity_type` falta o es `lead`; `element_id` solo si `element_type` falta o es `2` (lead). Un id de contacto/empresa nunca se toma por lead.
- **Motivos permanentes = se rinden YA** (`isPermanentReason`: `no_talk_id`, `no_kommo_credentials`, `not_lead_entity` —el PAYLOAD dice contacto/empresa—, `talk_lookup_capped`): no cambian entre intentos, no se reintentan. El resto es transitorio (incluye `talk_other_entity`). **Una fila SIN FIRMA no se reintenta nunca** (`planUnresolved`): se rinde en el primer intento con alerta agregada; un payload que pudo forjar cualquiera no repite consultas a Kommo 7 veces.
- **Sin resolver ≠ descartar**: la fila de `inbound_queue` vuelve a `pending` con `not_before` (espera 5/10/30/60/120/180 s < 7 min, `LEAD_RESOLVE_BACKOFF_SECONDS`; la primera es corta para que el mensaje entre antes del debounce de 45 s), un payload reducido a SOLO esos mensajes —cada uno con `_orig_idx`, su posición en el payload original, que decide el desempate de `created_at` (`messageOrderIndex`)— y `waiting_refs` (`talk:<id>`, `chat:<id>`, `contact:<id>`, solo ids validados). Los ya insertados no se reprocesan (`messages.kommo_message_id` es único). `claim_inbound_batch` (0092) no reclama filas con `not_before` futuro y devuelve `attempts`; tope `LEAD_RESOLVE_MAX_ATTEMPTS` = 7 claims. Si la fila no se puede reprogramar (0092 sin aplicar) queda `failed` con el motivo, nunca `done`. `done` limpia `last_error`, `not_before` y `waiting_refs`.
- **Orden de llegada (el primero no se responde aparte)**: msg1 sin lead espera; msg2 del mismo talk llega con lead. (a) `process-inbound` **despierta** la fila de msg1 (`not_before = now()` donde `waiting_refs && {talk,chat}` de msg2; `applyWakeFilter`: SOLO filas que siguen esperando el lead —`processing_failures = 0` y `last_error` `lead_unresolved…`—; una fila que volvió por una EXCEPCIÓN cumple su backoff de 60 s, si no el mensaje insertado a medias seguía «joven» (< 45 s) para el retomar y quedaba sin clasificar para siempre. Por lo mismo el reintento por excepción limpia `waiting_refs`, `processingRetryPatch`) y el drenado la toma en el lote siguiente de la misma invocación: msg1 entra con su `created_at` real (el más viejo). (b) `generate-response` (modo cola) **no responde** a un lead mientras su contacto tenga una fila `pending`/`processing` con `waiting_refs @> {contact:<kommo_contact_id>}` creada hace < `LEAD_WAIT_DEFER_SECONDS` (180 s; fail-open). Pasado ese tope se responde igual; si msg1 entra después de una respuesta ya enviada, se contesta aparte (aceptado).
- **Reaper coherente**: para filas con `waiting_refs` el reaper usa `v_lead_max_attempts` = `LEAD_RESOLVE_MAX_ATTEMPTS` (test de paridad en `lead-resolver.test.ts`), no el tope general de 5; si una de ellas muere procesando en su último intento, la cierra `failed` **con** la alerta (nunca silencioso).
- **Fallback sin la RPC**: solo ante `PGRST202`; respeta `not_before` si la columna existe y reserva cada fila con un UPDATE condicional (`status='pending'` + mismo `attempts`). Otro error de la RPC no cae al fallback: esa corrida no toma nada.
- **Agotado / descartado** (`planUnresolved` + `lossAlertMode`, solo si lo perdido es un mensaje `incoming`): alerta propia **`inbound_lead_unresolved`** (crítica, notificable, `onePerRef`: UNA por fila de la cola, `ref_id` = fila; metadata con motivos y talk/chat/contact **validados**, sin texto del cliente) + `console.error` SOLO si la fila llegó **FIRMADA** y era una conversación de lead que no se pudo ubicar. **Anti-inundación**: una fila **sin firma** (`inbound_queue.signed` false o NULL) la pudo forjar cualquiera con la URL → alerta **agregada** `inbound_dropped` (`aggregatedLossAlertFor`, una por ventana de 15 min); `no_talk_id`/`talk_lookup_capped` (forma desconocida) y `talk_other_entity` agotado (Kommo nunca asoció la conversación a un lead; motivo `lead_unresolved_entidad_no_lead`) también agregada; `not_lead_entity` (lo dice el payload) no es un mensaje para el agente → solo log. **Orden de deploy: 0092 ANTES que la función.**
- **`inbound_queue.signed` (0092)**: lo fija `kommo-webhook` al encolar (`decision.signed`: true = con el token). Sin la columna (0092 sin aplicar, PGRST204/42703) encola sin el marcador: nunca pierde el payload por eso, y la instancia guarda CUÁNDO la desactivó y la vuelve a probar a los `SIGNED_COLUMN_RETRY_MS` (5 min): una instancia caliente no queda encolando «sin firma» para siempre tras aplicar 0092. Una fila sin marcador cuenta como sin firma.
- **Fila que falla al procesar (`_shared/queue-failure.ts`)**: si `processPayload` lanza (hipo de la base/PostgREST, Kommo, un bug) la fila ya NO pasa directo a `failed`: vuelve a `pending` con `not_before` (60 s, 120 s) hasta `PROCESSING_MAX_ATTEMPTS` = 3 **fallas**, contadas en `inbound_queue.processing_failures` (0092, aparte de `attempts`: los claims gastados esperando el lead no se comen los reintentos de una excepción; `claim_inbound_batch` la devuelve). Queda por debajo de los topes del reaper 5/7 (test de paridad). Agotadas: `failed` + `last_error` saneado (`errorSummary`: sin valores entre comillas/paréntesis, que pueden ser texto del cliente) y, si el payload trae un mensaje `incoming`, alerta **`inbound_processing_failed`** (crítica, notificable, `onePerRef`, `ref_id` = fila; 0092 la suma al default, a las configs existentes y al índice único) si la fila llegó firmada, o agregada `inbound_dropped` si no (`processingLossAlertFor`). El reaper aplica la misma regla (firmada → por fila; sin firma → `insert_alert_aggregated`) y su texto dice «puede no haber entrado» (el worker murió a mitad: el mensaje pudo insertarse). **Cierres con red (L1)**: los UPDATE finales (`updateQueueRow`) chequean el error y, ante una columna de 0092 inexistente (42703/PGRST204), aplican el mínimo (`status`, `processed_at`, `last_error`): la fila nunca queda en `processing`. Idempotencia del reintento: el payload se re-procesa entero (leads por upsert, posiciones por `apply_lead_position`, mensajes por `kommo_message_id` único); un error al leer el duplicado o al insertar el mensaje (≠ 23505) lanza en vez de `continue`. No envía nada al cliente.
- **Retomar un mensaje insertado y sin clasificar (seguridad)**: el dedupe va ANTES del adjunto (un duplicado no se re-transcribe). Se retoma (`isResumableDuplicate`) SOLO si la fila guardada es del MISMO lead y dirección que el payload (un payload hostil puede reusar el `kommo_message_id` de otro lead), sigue sin vertical/clasificación y tiene más de `RESUME_MIN_AGE_SECONDS` (45 s < primera espera de 60 s) según `messages.inserted_at` (0092: hora REAL de inserción; `created_at` se sella con la llegada del webhook) — más joven puede estar clasificándose en otra invocación. La reserva es un UPDATE condicional (`claimResume`: mismas condiciones + `classification = {error: RESUME_CLAIM_ERROR, resume_at}` … RETURNING, `resumeClaimMarker`): de dos invocaciones gana una. `recoverFailedClassifications` NO toma una marca más joven que `RESUME_RECOVER_GRACE_SECONDS` (5 min; filtro `recoverResumeOrFilter` + `isFreshResumeMarker`): antes reclasificaba en paralelo el mensaje que se estaba retomando. Pasada la gracia el retomar se da por muerto y recover lo toma. Texto, canal y adjunto salen de la fila GUARDADA (`resumeInputsFromStored`), nunca del payload nuevo; las salidas «ignorado» limpian la marca.
- **Seguridad del payload (webhook público)**: `_orig_idx` lo escribe SOLO el reencolado propio; `kommo-webhook` lo borra de todo lo que llega (`stripOrderMarkers`), `messageOrderIndex` lo acota a `MAX_ORDER_INDEX` (999) y `created_at` nunca supera `now()`. El diferimiento de `generate-response` usa solo refs `contact:` **verificadas por la API de talks** (`verifiedContactId` del talk, no el `contact_id` del payload) y tiene un tope duro (`shouldDeferForWaitingRow`) medido desde el mensaje sin responder MÁS VIEJO del lead: filas nuevas no lo extienden.
- Forma de la API verificada contra la documentación de Kommo («Get conversation by ID»); no hay fallback por `contact_id` a propósito (un contacto puede tener varios leads).
- **Orden de locks de 0092**: `set local lock_timeout = '3s'`; primero `alerts` (DELETE de duplicados + índice único nuevo, lo lento) y AL FINAL `messages`/`inbound_queue`, que quedan bloqueadas lo mínimo hasta el commit. Tabla ocupada → la migración falla y se reintenta, sin encolar detrás a todo el tráfico.

### Ruteo de leads al equipo comercial (migraciones 0052/0053)

Reparte automáticamente los leads de una vertical entre el equipo de ventas, y estampa un campo del lead en Kommo. Vive en `supabase/functions/_shared/routing.ts` y lo llama `process-inbound` justo después de clasificar (tanto en el hot path como en `recoverFailedClassifications`).

- **Disparador**: `verticals.auto_assign = true`. El campo a completar sale de `verticals.kommo_field_name` / `kommo_field_value`, resueltos **por nombre** (misma filosofía que las tools de 0028). Se edita en `/verticales`.
- **Decisión**: si el texto del lead contiene un término de `routing_assignees.match_terms` (ej: su sede) → esa persona (`term_match`). Si no → `round_robin` vía la RPC atómica `next_round_robin_assignee(key)`, que serializa la rueda con `SELECT … FOR UPDATE` (sin eso, dos inbounds simultáneos le dan el mismo lead a la misma persona). El match normaliza mayúsculas/acentos y exige límites de palabra — un `includes` pelado hacía que "coro" matcheara dentro de "recordar".
- **Nunca roba leads**: solo asigna si el responsable EN VIVO en Kommo es `null` o está en `kommo_publish_config.routing_takeover_user_ids` (las cuentas genéricas). Si no se puede leer el responsable, no asigna.
- **Un lead se rutea una vez** (`leads.routed_at`). Única excepción: si se ruteó por `round_robin` (una suposición, porque no había sede) y un mensaje posterior SÍ nombra la sede, se corrige **una sola vez** — y solo si el responsable sigue siendo el que puso el sistema. Un `term_match` no se toca nunca. Sin esto, el CRM decía una cosa y el agente (que comparte el WhatsApp de la asesora de esa sede) decía otra.
- **Umbral de confianza (0056)**: `kommo_publish_config.routing_min_confidence` (default 0.80). Si la clasificación viene con menos confianza, se clasifica igual pero NO se toca el CRM ni se marca el lead como ruteado (un mensaje claro posterior sí lo rutea). Motivo real: una charla interna de staff (facturas, un chofer) se clasificó `eventos_corporativo` con 0.65 y le asignó un lead falso a una asesora. Clasificar con dudas es barato y reversible; escribir en el CRM de una persona real, no.
- **Auditoría**: cada decisión —incluidas las salteadas— queda en `lead_routing_events` con estrategia, término, responsable previo y motivo. Sin eso el round robin es una caja negra ante el primer "a mí no me llegó ninguno".
- Switches en `kommo_publish_config`: `routing_enabled` (kill switch, default OFF) y `routing_takeover_user_ids`. El equipo se administra en Ajustes → Agente → Acciones → "Ruteo de leads al equipo".
- **Campos `select` de Kommo**: hay que mandar `enum_id`, no `value` — con un string arbitrario Kommo devuelve 200 y **no guarda nada**. Usá `patchEntityFieldTyped`/`resolveFieldValue` (`_shared/kommo.ts`). `patchLeadField` sigue existiendo solo para campos de texto/textarea.

### Autenticidad del webhook de Kommo (`_shared/webhook-auth.ts`, migración 0073)

`kommo-webhook` es pública y Kommo no firma, así que el control es un secreto en la URL (`?token=`, tabla `_app_secrets.KOMMO_WEBHOOK_SECRET`; comparación en tiempo constante). **La decisión corre DESPUÉS de responder** (invariante 6): el handler contesta 200 y en `waitUntil` decide con el estado REAL de la base y encola o **descarta sin encolar** (Kommo recibe 200 igual: el emisor no se entera del rechazo; la auditoría queda en logs —sin el token—, en `kommo_webhook_auth.last_rejected_at/_reason` y en la alerta `webhook_rejected`, una cada 6 h). Un token presente pero incorrecto se descarta SIEMPRE. Sin token: modo `permissive` (transición de clientes vivos: se acepta y se alerta `webhook_unsigned`) o `strict` (descarte), en `kommo_webhook_auth`. Pasa a strict por el switch del dashboard o solo (requests firmadas + `strict_after_hours` (24) sin requests sin token).
- **Sin fail-open**: sin estado conocido no se acepta nada. Carga por instancia (`_shared/webhook-auth.ts`): caché 30 s, **una sola consulta en vuelo** (techo duro 5 s), stale-while-revalidate (vencido → último estado conocido, refresco en segundo plano), caché negativo de 2 s. Si el estado nunca se conoció (base caída al arrancar la instancia) se reintenta hasta 15 s y, si sigue caída, el payload se pierde con alerta `inbound_dropped` (`motivo: auth_state_unavailable`; con la base caída tampoco se podría encolar). 0073 sin aplicar (tabla inexistente) NO es un fallo: es un estado conocido = transición sin secretos.
- **Rotación**: atómica en la base (`kommo_webhook_rotate`): el vigente pasa a `KOMMO_WEBHOOK_SECRET_PREVIOUS` (vale 24 h). **Se rechaza (409)** si el anterior sigue vigente y Kommo no confirmó el actual (`current_confirmed_at` < `rotated_at`): rotar otra vez perdería el único secreto que Kommo tiene. Confirman: una request firmada con el VIGENTE (`kommo_webhook_note(p_current)`) o un «Actualizar en Kommo» exitoso (`kommo_webhook_mark_applied`, solo si el secreto sigue siendo el vigente). Una instancia caliente con el secreto viejo en caché, ante `bad_token` con caché de más de 1,5 s, **recarga una vez** (consulta compartida) antes de descartar. Si al rotar Kommo no se pudo actualizar, el panel lo muestra como ERROR con el botón «Actualizar en Kommo».
- **Pasar a estricto a mano**: el servidor responde 409 si nunca llegó una request con clave o llegó una sin clave hace < 1 h (`strictModeBlocker`), salvo `force: true`; el panel muestra el motivo y pide confirmación explícita.
- **El secreto no sale del panel**: `/api/kommo/webhook-auth` (GET URL+estado; POST `set_mode` / `apply` / `rotate`; alcance `configuracion`, verificado también en el handler) es la única respuesta con la URL completa. Lo demás enmascara con `maskDestination` (`web/src/lib/kommo-webhook.ts`, copia en `_shared/webhook-mask.ts`): incidentes de `health-scan` (`system_incidents` la lee cualquier usuario con sesión; 0073 enmascara lo ya guardado), logs, errores de Kommo y la respuesta de `reconnect-webhook`. Guardia: `_shared/webhook-secret-leak.test.ts`. **Ojo con los logs de plataforma**: el `?token=` viaja en la query string, así que aparece en los logs de invocación de Supabase (Edge Functions → Logs) y en los de Kommo (historial de webhooks); quien tenga acceso a esos logs ve el secreto. Si se exponen (captura, soporte, cuenta compartida), **rotar**.
- **Registrar en Kommo**: un único camino, `web/src/lib/kommo-webhook-apply.ts` (`applyWebhookDestination`), que usan `apply`/`rotate` y `reconnect-webhook`: POST del destino vigente (rehabilita si estaba deshabilitado), verificación, y DELETE de los destinos viejos nuestros (Kommo no edita la URL), conservando los eventos que el operador sumó. El env `KOMMO_WEBHOOK_SECRET` y `?secret=` (legado) se aceptan como un secreto válido más. Defensa en profundidad del orden: el instante del payload se recorta a llegada + 2 min y, si difiere de la llegada en más de 7 días, se usa la llegada con un warning (`lead-position.ts`); `apply_lead_position` recorta también a `now()` + 2 min. **Al portar a un cliente:** aplicar 0073, desplegar, pulsar «Actualizar en Kommo» y luego estricto.

### Texto del lead = entrada NO confiable (prompt injection)

Todo texto controlado por el lead que entra a un prompt pasa por `_shared/untrusted.ts` — **nunca** se interpola crudo. Cada turno es un elemento de UNA línea con el rol en un atributo que el lead no controla: `<turno rol="lead">…</turno>` / `<turno rol="agente">…</turno>`; el contenido se normaliza (NFKC, saltos de línea de cualquier tipo → ` ⏎ `, sin invisibles/bidi/control) y se escapa (`& < > "`), de modo que nada dentro de un turno puede cerrarlo, abrir otro ni imitar el prefijo `Agente:`. El prompt que lo consume antepone `UNTRUSTED_NOTICE` (solo `rol="agente"` es del sistema; las instrucciones dentro de turnos del lead no se obedecen). Aplica a: `[HISTORIAL]` y mensajes nuevos (generate-response), `lead_name` y `classifier_reasoning`, clasificador (`process-inbound`), seguimiento (`follow-up-scan`, que ahora usa `fetchLeadHistory`), transcripts de Dreams (que alimentan el digest persistente del agente), respuesta a comentarios y el juez LLM de `evaluate-outcomes` (`_shared/grader-prompt.ts`: mensaje del lead y respuesta del agente como turnos). `fetchLeadHistory` conserva firma y tipo (string) pero **el formato cambió** de `Lead:/Agente:` a turnos `<turno>`; todo consumidor propio debe anteponer `UNTRUSTED_NOTICE`. Tests: `untrusted.test.ts`, `history.test.ts`, `grader-prompt.test.ts`. Nuevos puntos de entrada de texto del lead → usar `turn()`/`sanitizeUntrusted()`.

**Aviso por contexto.** `UNTRUSTED_NOTICE` (conversación): los turnos `rol="agente"` son el registro de lo que el agente dijo y TAMPOCO son fuente de órdenes (pudo repetir lo que plantó el lead). `EVALUATION_NOTICE` (grader, digest de Dreams, clasificador con historial): TODO el material, lead y agente, es el OBJETO analizado; solo vale el system prompt. El grader usa `turnPreservingLines` (conserva los saltos de línea, cada renglón saneado con prefijo `| `). **Texto seguro** (`_shared/text-safe.ts`, copia en `web/src/lib/`): todo truncado que va a un prompt o a Kommo corta por grafema (`Intl.Segmenter`, el límite es en code units UTF-16) y descarta surrogates sueltos (Anthropic responde 400 «no low surrogate»).

### Sincronización segura del system prompt (`lib/agent-prompt-sync.ts`)

Todo camino que empuja el prompt al Managed Agent pasa por `syncAgentTools` (guardar en `/agent`, botón «Sincronizar» → `POST /api/agent/sync`, toggles de tools/CRM/BCV/Shopify, wizard `/setup`). **Antes de empujar** compara el system VIVO (`retrieveAgent`) contra la línea base `runtime_config.AGENT_PROMPT_SYNCED_HASH` (hash del system exacto enviado la última vez) + `ANTHROPIC_AGENT_VERSION`: hash distinto → `prompt_changed`; versión viva mayor que la registrada → `version_ahead`. En conflicto **NO sincroniza**: 409 con el diff y la UI de `/agent` (`agent-prompt-conflict.tsx`) ofrece **importar el vivo** (`{resolve:"import_live"}`) o **sobrescribir** (`{resolve:"overwrite"}`). Tests: `pnpm test` en `web/` (requiere **Node >= 22.18**: `node --test` ejecuta los `.ts` con type-stripping nativo; `engines` en ambos `package.json` y `web` es `"type": "module"` para evitar el reparseo).

- **Qué difiere, exacto**: el conflicto trae `scope` (`operator` | `scaffold` | `both` | `none` | `unknown`), `diff` SOLO del prompt del operador y `scaffoldDiff` aparte (el scaffold/acciones de tools es del código). Nunca se mezclan en un diff.
- **Primera sincronización (clientes que actualizan, sin hash)**: se compara SOLO el prompt de operador vivo (`extractOperatorPrompt`) contra el `SYSTEM_PROMPT` de la DB ya sustituido. Igual → se adopta (el push registra el hash) aunque el scaffold viejo difiera; distinto → conflicto `first_sync_differs`. `/api/usage/models` usa `checkAgentPromptConflict(…, {onlyWithBaseline:true})`: no empuja el prompt, así que sin hash no se bloquea el cambio de modelo.
- **Línea base siempre fresca**: `readBaseline()` lee hash/versión DIRECTO de la tabla (`configValuesFresh`, sin la memoización por request). Ante un 409 el reintento (`lib/guarded-push.ts`) la RELEE: un sync concurrente o un rename pudo moverla.
- **Renombrar el agente sube su versión**: usar siempre `renameAgent` (`sync-agent-tools.ts`), que registra la versión devuelta (`lib/agent-rename.ts`; no la registra si el agente ya iba por delante por una edición externa). `renameResource` ya no acepta `agents`.
- **`import_live` re-placeholderiza** (`lib/prompt-placeholders.ts`, inversa de `substitutePlaceholders`): rutas `/mnt/memory/<store>` y nombres como tokens completos, más largo primero, una sola pasada. Valores ambiguos (<4 caracteres, palabras comunes como los defaults `el operador`/`master`/`leads`, o dos placeholders con el mismo valor) NO se tocan y el panel los muestra.
- **`import_live` restituye también `{{TOOLS_LIST}}`**: `renderToolsList` (agent-prompt.ts) es el único que arma ese bloque; `placeholderize(text, values, {toolsList})` lo vuelve a `{{TOOLS_LIST}}` por coincidencia exacta. Sin herramientas HTTP el bloque es `""` y no hay nada que recuperar. Con `SYSTEM_PROMPT` vacío el scaffold queda AL INICIO del system: `extractOperatorPrompt` lo tolera (operador `""`).
- **TOCTOU de la resolución**: el conflicto trae `liveHash` (hash del system vivo mostrado). `POST /api/agent/sync` con `resolve` EXIGE `expectedLiveHash` (400 si falta); si el vivo cambió entre mostrar y resolver, se aborta con 409 `{stale:true}` (+ el conflicto actualizado) y el panel pide revisar de nuevo. La guardia corre dentro de `guardedPush`, en el mismo intento que empuja (`checkResolveHash` para `import_live`).
- **Formularios con estado local derivado de config** (`AgentForm`): `key={formKey(...)}` (`lib/form-key.ts`). Sin la key, tras «Importar el vivo» el `useState` conservaba el prompt viejo y el próximo «Guardar y sincronizar» lo pisaba sin conflicto. Los demás paneles (BCV, comentarios, horario, modelos) solo cambian por su propio guardado, no por import/resolución.

### Texto saliente: un único verificador y un único «lo enviado» (`_shared/outbound.ts`)

- **`draftText(d)` = `edited_body` (si no está vacío) o `body`** (`_shared/draft-text.ts`; copia exacta en `web/src/lib/draft-text.ts`). Es lo que se PUBLICA. Antes `publish-to-kommo` y su guard leían solo `body`: lo que el operador corregía en el inbox NUNCA llegaba al cliente. Lo usan publish-to-kommo, el guard, el historial, Dreams, los graders y el inbox; **nunca** `d.body` ni `edited_body ?? body` a mano.
- **Todo texto a Kommo sale por `outbound.ts`**: `writeClientText` (DM, respuesta pública a comentarios de IG, variables del seguimiento) y `writeCrmField` (valores que el modelo elige en las tools de CRM) verifican con `detectInternalLeak` ANTES de tocar la API y lanzan `OutboundBlockedError`. Ningún otro código llama a `patchLeadField`/`patchContactField`/`runSalesbot` (el test `outbound.test.ts` falla si aparece un camino sin verificar).
- Comportamiento: **fuga en el DM** → el draft vuelve a `pending` con `guard_blocked` (se verifica ANTES de publicar la parte pública, para no duplicar el comentario al reaprobar). **Fuga solo en la pública** → se omite la pública, el DM sale si está limpio, el draft queda marcado `guard_part=public_reply` y alerta `outbound_blocked` (0068; sale también al webhook de alertas). **Seguimiento** → `failed` con el motivo, alerta y cooldown (se verifican todas las variables antes de escribir la primera). `generate-response` aplica el mismo verificador a la respuesta pública al generarla. El inbox muestra el motivo y marca «editado».

### No responder a propósito vs. falla (`_shared/agent-output.ts`, migración 0087)

El protocolo de salida del agente tiene DOS cierres: `<respuesta>texto</respuesta>` o `<sin_respuesta>motivo</sin_respuesta>` (lo explica `NO_REPLY_INSTRUCTION` en el `[CONTEXTO]` de cada sesión: no requiere re-sync del agente). Antes no existía el segundo: cuando el prompt del operador decía «solo emojis / reacción / spam → no respondas», el agente cerraba con `<respuesta>\n</respuesta>` y el draft quedaba `failed` («agent devolvió respuesta vacía») con alerta `draft_failed`, sin `session_id` y sin registrar el consumo (SuperCines, oct-2026: ~2–3 % de los drafts).
- `<sin_respuesta>` → draft **`skipped`** (terminal, `body = ""`, `agent_metadata.no_reply_reason` + `session_id`): no se publica, no alerta, el lote queda cubierto (`answered_by_draft_id`) y no se reprocesa. El inbox lo muestra como «sin respuesta».
- Bloque vacío o turno sin texto NO es una decisión: se le pide en la MISMA sesión que elija (`emptyOutputCorrectionMessage`, comparte `MAX_LEAK_RETRIES`). Texto sin bloque (análisis «no respondo») va al verificador de fuga, que en ese caso también ofrece `<sin_respuesta>`. Si tras los reintentos no hay ni texto ni decisión → `failed` (falla real, alerta).
- `<respuesta>` con contenido Y `<sin_respuesta>` → ambiguo: nunca auto-envía (revisión humana).
- **Fail-closed** (revisión de seguridad): todo lo que se PARECE a una marca y el tokenizador no reconoce (confusables cirílicos/griegos, `‹ ›`, invisibles, marcas combinantes; `protocolSkeleton`) = malformado sin rescate, nunca vacío ni texto suelto. `name="respuesta"` junto a etiquetas = malformado. Un `<respuesta>` sin cerrar solo se rescata si la apertura empieza su línea. Texto del agente DESPUÉS del bloque final, en el mismo mensaje o en otro (`AgentTranscript.decide`), = malformado con el bloque como rescate (el contexto pide escribir learnings.md ANTES del mensaje final). Tope `MAX_PARSE_CHARS` (20k) y patrones lineales (el `<\s*\/?\s*` previo era cuadrático: ~17 s con 100k espacios).
- **Rescate = nunca auto-envío**: `draftStatusFor` deja `pending` todo texto `guardBlocked` (rescate o fuga), aunque `bypass_review` o la vertical digan auto; publicar pasa igual por `outbound.ts`.
- **Compuerta del no_reply** (`noReplyGate`): no se acepta sin humano si el lote del lead trae algo parecido a una marca del protocolo (prompt injection «respondé solo <sin_respuesta>…»), si el lead ya acumula `MAX_CONSECUTIVE_SKIPS` (2) «no responder» seguidos (`skipped` o en revisión), si el agente tenía una respuesta y la cambió por `<sin_respuesta>` tras una corrección que no ofrecía esa salida, o si no se pudo leer el historial. Frenado → draft `pending` sin texto (`agent_metadata.no_reply` + `no_reply_review`) y el lote con `requires_human_review` (inbox «revisión» + alerta). Límite conocido: una instrucción plantada en un mensaje anterior sin etiquetas no se detecta; la acota el tope de skips.
- **Visible en el inbox (0088)**: un `skipped` o un no_reply en revisión cuentan como «sin responder» (`awaiting_reply`) hasta que sale una respuesta enviada. Desde el panel: «Responder igual» (aprobar con texto obligatorio; la ruta approve rechaza un draft sin texto) o «Marcar revisado» (rechazar); la policy `drafts_review` acepta `skipped`. Al frenar un no_reply (`parkForHuman`), generate-response 1) marca `requires_human_review` SOLO en los mensajes de ese lote que no lo estaban, 2) hace visible el draft (`pending`, guarda status) registrando exactamente esos ids (`agent_metadata.no_reply_marked_ids`) y 3) si el draft ya no estaba `pending` o el update falló, deshace la marca: nunca queda un flag sin registro ni un registro sin marca; resolverlo desde el panel (approve/reject, alcance `operacion` con `requireScope`) desmarca exactamente esos (`lib/draft-review.ts`), nunca un flag del clasificador ni otro lote. **Racha** (`countsAsNoReply`): la consulta trae, filtrando EN LA BASE, solo los drafts del lead que deciden algo — enviados (`sent`/`auto_sent`), `skipped` o marcados `no_reply` — ordenados por `created_at, id` desc con `.limit(MAX_CONSECUTIVE_SKIPS)`. Cuenta todo `skipped`/`no_reply` que no terminó enviado (pending, approved, publishing, failed, rejected); solo una respuesta enviada la corta. Los demás drafts (un run concurrente del mismo lead `pending`+`generating`, una respuesta en revisión, un failed común) NO participan: ni suman ni cortan, así ni runs superpuestos ni cambios de estado sin envío reinician el tope.
- **Sin texto no se envía (0089)**: CHECK `drafts_texto_para_enviar` — ningún draft llega a approved/publishing/sent/auto_sent sin texto (`edited_body` o `body` con algún carácter que no sea espacio, incluidos los espacios Unicode que quita `trim()`), ni por PostgREST con la sesión del panel. La migración primero devuelve a `pending` (guard «texto vacío») los approved/publishing viejos sin texto: si no, reservarlos fallaría en cada corrida y trabaría la cola de publicación. Además la ruta approve devuelve 400 y `outbound.ts` bloquea «texto vacío» al publicar.
- **Un solo parse** (`parseProtocol`): la decisión, el texto extraído y «qué mensaje cuenta» (`AgentTranscript`: gana el último `agent.message` con marcas; sin marcas, el último) salen del MISMO tokenizado de las marcas. El texto de una respuesta sale SOLO de adentro de un bloque `<respuesta>` bien formado (o, como rescate a revisión humana, de un `<respuesta>` sin cerrar / `name="respuesta"`); NUNCA del crudo. Anidar, cerrar sin abrir, dos respuestas con contenido o marcas con caracteres no ASCII (`＜respuesta＞`) = malformado. Texto sin ninguna marca = malformado sin rescate (antes se rescataba el crudo para revisión). Los strings que van al modelo usan tuteo (sin voseo), lo verifica el test. Un draft `failed` guarda siempre el `session_id` y la sesión se contabiliza en `usage_events` (el techo de gasto ya no ignora las fallidas).
- **Orden de deploy: 0087 (y 0088, 0089) ANTES que la función** (sin el CHECK nuevo el UPDATE a `skipped` falla, el draft queda `pending` y el barrido de runs muertos reprocesa el lote).
- **SuperCines**: `<sin_respuesta>` se decide ANTES de `leakOf()` (la red propia con `INTERNAL_REASONING_RE`: «no respondo», «análisis interno»…), así que una no-respuesta explícita nunca se confunde con una fuga; `leakOf` sigue vigilando el texto de `<respuesta>` y el texto sin bloque.

### Publicación a Kommo: reserva por draft y a lo sumo un envío (`_shared/draft-publish.ts`, migración 0074)

Antes, `publish-to-kommo` leía los `approved` con un SELECT y publicaba (PATCH + salesbot + verificación de hasta 12 s por draft) ANTES de responder: el cron, la aprobación del panel y `generate-response` enviaban el mismo draft, y si el llamador cortaba (panel 4 s, pg_net 30 s) el runtime la mataba con el salesbot ya disparado y el draft seguía `approved` → el barrido lo reenviaba (WhatsApp duplicado). Ahora:

- **Estado `publishing`** (= «enviando…»): `claim_draft_for_publish` reserva de a UN draft (`approved → publishing`, `publish_owner` = id de la invocación, lease de 10 min > wall clock de una Edge Function; `for update skip locked` + guarda de estado: de dos reservas concurrentes gana una).
- **Write-ahead antes de cada salesbot** (`mark_draft_publish_sending`: fija `publish_sending_at` y la foto `publish_baseline` de salientes del lead). Solo el dueño y con el lease vigente; si falla, no se dispara nada. Escribir el campo (PATCH) no le manda nada al cliente — supuesto: la cuenta no tiene un trigger de Kommo que dispare un bot al cambiar ese campo.
- **Reserva muerta** (`recover_dead_draft_publishes`, al inicio de cada corrida): sin marca → vuelve a `approved` (a las 3 reservas muertas → `failed`); **con marca → NUNCA se reenvía**: se compara la foto con los salientes actuales → `auto_sent` (`delivery_recovered`) si apareció uno nuevo, si no `failed` + alerta `salesbot_not_delivered` («revisá si le llegó»). Preferimos un mensaje que quizás no llegó (con alerta) a uno duplicado. Muerte entre la respuesta pública de un comentario y el DM → sin foto del DM → `failed` + alerta (reenviar duplicaría el comentario público).
- Toda escritura final lleva la guarda `status='publishing' AND publish_owner=<yo>`. El panel no puede tocar un `publishing` ni des-enviar un `sent`/`auto_sent`: las rutas `approve`/`reject` filtran por estado (409) y el trigger `drafts_guard_in_flight` lo impide en la base para cualquier petición con JWT de usuario. Lista de estados en `web/src/lib/draft-status.ts` (test de paridad con el CHECK).
- Tests: `_shared/draft-publish.test.ts` (decisiones y carrera cron vs. manual), `supabase/tests/draft_publish_claim.sql`.

### Seguimiento automático: reserva por lead y paso, a lo sumo un envío (`_shared/followup-claim.ts`, migración 0075)

`follow_up_due_leads` no reservaba nada: el cron de `follow-up-scan` corre cada 5 min pero un barrido con varios leads (~60 s de sesión del agente por lead, hasta 400 s de wall clock) dura más, así que dos barridos superpuestos —o el reintento manual del panel contra el barrido— le mandaban la MISMA plantilla al MISMO lead. Ahora, mismo patrón que 0074:

- **La reserva es la fila del intento en `follow_ups`** (estado `claimed` = «Enviando…»): `claim_follow_up(lead, paso, …)` lockea la fila del lead, exige que el paso siga siendo `follow_up_step + 1` (si otro ya lo envió → `step_changed`) y la crea con dueño (`runId` de la invocación) y lease de 10 min. Índices únicos: una `claimed` por lead, y una `claimed`/`sent` por (lead, paso) → de dos reservas gana una y un paso no se registra dos veces. Se toma ANTES de gastar la sesión del agente; el barrido y `retryOne` (reintento manual) usan la misma. `follow_up_due_leads` excluye lo bloqueado (`follow_up_block_reason`) para que no ocupe lugares del barrido.
- **Write-ahead antes del salesbot** (`mark_follow_up_sending`: `sending_at` + foto `baseline` de salientes + variables). Solo el dueño con el lease vigente; si falla, no se dispara nada.
- **Cierre atómico**: `finish_follow_up` registra `sent` y avanza el lead (paso, `follow_up_last_sent_at`, `active`/`exhausted`; respeta `responded`/`stopped` llegado mientras se enviaba) en UNA transacción, con guarda de dueño. `release_follow_up_claim` borra la reserva cuando no hubo intento (skip/stop/whitelist/etapa); con la marca puesta no se puede soltar. Un fallo después de la marca siempre se cierra como «sin confirmar» (`runClaimedFollowUp`).
- **Reserva muerta** (`recover_dead_follow_up_claims`, al inicio de cada invocación, incluso con el techo de gasto): sin marca → `failed` + `interrupted` (no salió nada; se reintenta; a las 3 interrupciones del mismo paso, `follow_up_max_interrupted()`, el barrido deja de reintentarlo y queda para el botón); **con marca → NUNCA se reenvía**: se compara la foto con los salientes actuales → `sent` (confirmado: un `outgoing_chat_message` DE ESE LEAD que no estaba en la foto y con `created_at` posterior a `sending_at`; `_shared/draft-publish.ts` `resolveInterrupted`, compartido con 0071) o `failed` con `sending_at` = **«sin confirmar»** + alerta `salesbot_not_delivered`. Un paso sin confirmar no lo reintenta el barrido; el panel lo muestra como «Sin confirmar» y el botón «Reenviar» exige confirmar (`confirm_resend`).
- **Reintento manual POR INTENTO** (migración 0077): el botón manda `{ followUpId, step }` de la fila (`/api/follow-up/retry` → `follow-up-scan` `{ follow_up_id, step, force?, confirm_resend? }`; `_shared/followup-retry.ts` `parseScanRequest`/`evaluateRetryGate`). Se reintenta solo si `step = follow_up_step + 1` y ese intento es el ÚLTIMO de su (lead, paso) — lo verifica `claim_follow_up(…, p_attempt_id)` con el lead lockeado (→ `superseded`); si no, **409** con el motivo. `p_confirm_resend` exige `p_manual` + `p_attempt_id`: la confirmación queda atada al intento que la persona revisó. «Último» = orden `(sent_at desc, id desc)`; la reserva fija `sent_at = clock_timestamp()`. El panel solo muestra el botón en el último intento fallido de cada (lead, paso) (`web/src/lib/follow-up-retry.ts` `latestAttemptIds`).
- **Variables de la plantilla = texto no confiable** (`_shared/followup-variables.ts` `resolveTemplateVariables`): solo propiedades PROPIAS del JSON del agente (`Object.hasOwn`), en un mapa `Object.create(null)` con exactamente las variables de la plantilla. Una variable llamada `constructor`/`toString` ya no «se completa» con lo heredado de `Object.prototype`. Mismo criterio en `interpretClaim` (motivo de la base).
- **Kommo ilegible ≠ «sin salientes»**: `fetchOutgoingEvents`/`fetchOutgoingEventIds` (`_shared/kommo.ts`) devuelven `null` si no pudieron leer (red, HTTP no-OK, forma inesperada; 204 = `[]`). Foto fallida → `baseline = null`; lectura fallida al recuperar → `null`; en ambos casos el corte queda «sin confirmar», nunca «enviado». Un set vacío por error hacía pasar cualquier saliente posterior (una respuesta manual, otro lead) por la entrega.
- El panel solo LEE `follow_ups` (RLS `authenticated_read`): borrar una reserva o insertar un `sent` desde el panel habilitaría un duplicado. Envíos duplicados previos a 0072 quedan como `duplicate` en el log.
- Tests: `_shared/followup-claim.test.ts`, `_shared/followup-delivery.test.ts` (Kommo falso: foto fallida, saliente anterior a la marca, de otro lead, posterior del lead), `_shared/followup-retry.test.ts`, `supabase/tests/follow_up_claim.sql` (+ carrera real con dos sesiones psql: la segunda espera el lock del lead y recibe `in_flight`).

**Inventario de envíos al cliente** (todo lo que dispara un salesbot): solo `publish-to-kommo` (drafts: DM y respuesta pública a comentarios de IG; reserva de 0074) y `follow-up-scan` (plantillas; reserva de 0075). `generate-response`, la reactivación tras pausa (`process-inbound` → `generate-response`) y el panel (aprobar/editar) solo crean o aprueban drafts, que salen por la reserva de 0074; `claim_message_batch` (0060) evita dos drafts para el mismo lote de mensajes. `alerts-scan` solo avisa al operador (webhook), `dreams-run`/`evaluate-outcomes` no envían. Un camino nuevo que le escriba al cliente DEBE pasar por una de las dos reservas.

### EXECUTE de las funciones SQL (la anon key es pública)

Postgres da EXECUTE a PUBLIC en toda función nueva y Supabase agrega default privileges para anon/authenticated: una función con EXECUTE para `anon` la invoca cualquiera con la URL del proyecto, y una SECURITY DEFINER bypasea la RLS. Las migraciones **0063** (ya aplicada en producción), **0070** y **0072** cierran todo: REVOKE de PUBLIC/anon/authenticated sobre TODAS las funciones propias de `public` (las de pgvector/pg_trgm, que viven en `public`, no se tocan), GRANT explícito a `service_role` y, a `authenticated`, solo lo que el panel llama por RPC con la sesión (`inbox_board`, `inbox_page`, `inbox_stats` y las puras `inbox_filter_sql`/`inbox_etapa_agente_sql` del inbox paginado, 0085; `gasto_mes_actual` salió en **0079** porque lee `runtime_config`: `/consumo` la llama con service_role); `ALTER DEFAULT PRIVILEGES` para que las futuras no nazcan abiertas. Las SECURITY DEFINER llevan `set search_path = public, pg_temp` y un guard interno (`end_user_request()`: rechaza peticiones con claims de usuario aunque alguien re-otorgue EXECUTE). **Función SQL nueva** → si la usa el panel con la sesión, `grant execute … to authenticated` explícito en SU migración y agregarla a la lista de `supabase/tests/function_execute.sql`; si la usan Edge Functions/cron, nada (service_role ya la tiene por default privileges). Prueba: `supabase/tests/function_execute.sql` (y `claim_kommo_backfill.sql`) contra un Postgres con todas las migraciones aplicadas.

### Headers de http tools: secretos atados a sus hosts (`lib/http-tool-keys.ts`, migración 0078)

Una tool puede poner `{{CLAVE}}` en sus headers; el servidor la resuelve y la manda a la URL que la tool define, que define quien la edita (o el modelo, con un `{{param}}`). Una lista de claves no alcanza: cada SECRETO queda atado a sus hosts de destino y la decisión se toma con la URL FINAL ya interpolada.
- `KOMMO_ACCESS_TOKEN` solo viaja por https al host EXACTO de `KOMMO_API_DOMAIN`.
- `TOOL_<X>` (secretos propios del operador, en `runtime_config`) solo viajan a los hosts que el operador declara en `TOOL_<X>_HOSTS` (lista separada por comas, host exacto); sin esa declaración no se resuelven.
- `KOMMO_API_DOMAIN` / `KOMMO_SUBDOMAIN` no son secretos: se resuelven como datos.
- `ANTHROPIC_API_KEY`, `SUPABASE_*` y cualquier otra clave: NUNCA (ninguna tool legítima las usa). Nunca `process.env`.
- Host con `{{param}}` en la plantilla + secreto → rechazado (el modelo no puede mover el host). Clave no permitida, host no atado → la llamada se RECHAZA con un error claro (no se manda el header vacío).
- Con un secreto en los headers el fetch va con `redirect: "manual"` (un 302 no lleva el header a otro host).
- **Sin «parser differential»**: `resolveToolHeaders` parsea la URL final UNA vez (`parseToolUrl`), valida el host sobre ese objeto y devuelve `url` (la `href` normalizada): el fetch se hace SIEMPRE con `resolved.url`, nunca con la cadena interpolada. Se rechaza antes de parsear lo que dos parsers leen distinto: no-ASCII, espacios/tabs/CR/LF/controles, backslash, `%00`, y en la autoridad `@` (userinfo), `%` y corchetes; además `url.hostname` debe ser idéntico al host escrito (si el parser lo reescribe —`127.1`, `0x7f.1`, `2130706433`— es un diferencial). Con un secreto en juego también: solo puerto 443, host «atable» (`isBindableHost`: ≥ 2 etiquetas válidas, sin punto final, TLD con letra → ninguna IP literal ni IPv6, nunca `localhost`). Se exige ASCII: un host IDN solo coincide si el operador declaró exactamente su `xn--…`. Tests: tabla de URLs de ataque + propiedad (fuzz) «toda URL aceptada es `new URL(url).href` y su hostname está permitido».
- **El runtime es el ÚNICO que resuelve secretos guardados** (`generate-response`, copia en `_shared/http-tool-keys.ts` con test de paridad), y los lee SOLO de la tabla: `cfg.getDbOnly(k)` (`_shared/config.ts`), sin fallback a `Deno.env` (un `{{CLAVE}}` ausente en la base no puede caer en un secret de las funciones con el mismo nombre). Un secreto sin valor RECHAZA la llamada (no se manda `Bearer ` vacío).
- **El probador (`/api/tools/test`, alcance `configuracion`) NO resuelve ningún secreto**: lee de `runtime_config` solo claves PÚBLICAS con `publicConfigValues(publicKeysForHeaders(headers))` (DB-only, consulta solo esas filas y lanza si se le pide una secreta): `KOMMO_API_DOMAIN`, `KOMMO_SUBDOMAIN` y los `TOOL_<X>_HOSTS`. Cada `{{KOMMO_ACCESS_TOKEN}}`/`{{TOOL_<X>}}` se sustituye por el valor de prueba que el operador pega en el panel (inputs `password` derivados con `secretKeysInHeaders`, mandados como `testSecrets` en el body; no se guardan en la tool, ni en localStorage, ni se persisten o loguean en el servidor). Sin valor tecleado → 400 «En el probador pegá el valor de prueba de {{K}}». Aplica el mismo `resolveToolHeaders` (mismo atado a hosts que el runtime). Guardias en `http-tool-keys.test.ts`.
- Leer, crear o editar `agent_tools` exige alcance `configuracion` en la API (middleware) y en la RLS (0078: select/insert/update/delete solo con `admin`/`configuracion` en el JWT; sin rol, otro alcance o `anon` no ven ni una tool: las URLs y qué secreto usa cada header no son de su incumbencia).
**Al portar:** una tool que usara otra clave en un header debe moverla a `TOOL_<NOMBRE>` en `runtime_config` + `TOOL_<NOMBRE>_HOSTS`. Desde **0079** `runtime_config` no es legible ni escribible con la sesión (solo service_role, tras `requireScope("configuracion")`): nadie puede mover `KOMMO_API_DOMAIN` ni `TOOL_X_HOSTS` por PostgREST (ver «Secretos y runtime_config»).


### Alertas y notificación por webhook (Slack/Discord) — `_shared/alert-kinds.ts`, `_shared/alerts.ts`, migración 0076

- **Registro único** de tipos (`ALERT_KINDS`, `as const`: va o no va al webhook, tabla y motivo). `AlertKind` = unión derivada del registro (solo los de la tabla `alerts`; los incidentes de salud viven en `system_incidents`).
- **Insertar = `insertAlert(supabase, { kind: AlertKind, … })`** (`_shared/alerts.ts`), OBLIGATORIO para todo insert a `alerts` desde las Edge Functions: un tipo no registrado no compila (`npm run check`). `alert-kinds.test.ts` falla si queda un `from("alerts").insert/upsert` fuera del helper (funciones y `web/src`), si un tipo insertado (llamadas a `insertAlert`, filas armadas aparte como `plan.row` —objeto con `kind` + `severity`—, constantes `satisfies AlertKind`, y el SQL `insert into alerts|public.alerts|"alerts"` con `values` de una o varias filas o `select`, en cualquier orden de columnas) no está registrado, o si el default de `alert_config.webhook_kinds` (0076) diverge del registro. El helper escribe SOLO columnas del esquema base (nunca `webhook_*`) y nunca lanza (`{ error }`).
- **UNA alerta por entidad (0091):** `draft_failed` y `human_review_needed` (`onePerRef` en el registro) tienen índice único parcial `(kind, ref_id)`: la base rechaza la copia (23505) e `insertAlert` la devuelve como `{ error: null, duplicate: true }`, no como error. Sin eso, el chequeo previo de `alerts-scan` (`existingAlerts`) era un bucle: PostgREST corta en 1.000 filas y el error se tragaba, así que pasadas las 1.000 alertas de las últimas 24 h lo que quedaba fuera del corte se volvía a crear cada 5 min (la «ráfaga» de 282 mil `draft_failed` de 0055; en un despliegue sin retención, 2,7 millones de filas y el Disk IO Budget agotado). `existingAlerts` consulta de a 200 y, si falla, ese barrido no crea ninguna. Un tipo nuevo que sea «una por entidad»: `onePerRef: true` + migración que amplíe el índice (y apuntar a ella el test de `alerts.test.ts`, que hoy lee 0091). Índice `(kind, created_at)` para todas las consultas por tipo.
- **Entrega (un solo camino):** `alerts-scan` (cada 5 min) crea sus alertas con el helper (nacen pendientes) y después barre TODAS las pendientes (`webhook_notified_at is null`) con `claim_alerts_for_webhook(p_kinds = webhook_kinds del operador)`: toma `pg_advisory_xact_lock(hashtextextended('alerts:webhook_sweep', 73))` (dos barridos se serializan: el dedupe no tiene carreras) + `for update skip locked`; cierra sin postear las de más de 24 h y las de tipos no notificables (no gastan cupo); **rate limit** 10 por barrido; **dedupe**: una idéntica (tipo + título + `ref_id`) a otra **efectivamente posteada** (`webhook_posted_at`) hace menos de 1 h se suprime, y entre idénticas del mismo lote sale la más vieja con `repeated` = suprimidas → el aviso dice «(+N repetidas)». `webhook_posted_at` lo marca el reclamo y alerts-scan lo vuelve a null si el POST falla: un aviso que no llegó no suprime al siguiente, y un POST fallido no se reintenta (se prefiere perder un aviso a duplicarlo). Lo descartado por viejo o backfilleado nunca cuenta para el dedupe. Sin webhook activo no se reclama nada.
- **Cuerpo del aviso** (`_shared/alert-webhook.ts`, también lo usa `health-scan`): Slack lee `text` (se escapan `&`, `<`, `>`: sin `<!channel>`, `<@U…>` ni links `<url|texto>` ajenos, p. ej. un `display_name` hostil); Discord lee `embeds` (se cortan `@everyone`/`@here`, `<@…>`, `<#…>` y `[texto](url)` con un espacio de ancho cero, más `allowed_mentions: { parse: [] }`).
- **Orden de deploy: 0076 ANTES que las funciones** (el panel de actualizaciones ya aplica migraciones → funciones). Si se invierte no se pierden alertas (el insert no toca columnas de 0076) y `alerts-scan`, ante `PGRST202` (RPC inexistente), postea directo lo que crea él mismo como antes; lo que inserten otras funciones en esa ventana queda en `/alerts` (el backfill de 0076 lo marca notificado al aplicarse; no marca `webhook_posted_at`).
- **Notificables:** draft_failed, human_review_needed, outcomes_regression, inbound_silence, inbound_dropped, kommo_webhook_disabled, budget_exceeded, outbound_blocked, salesbot_not_delivered, provider_credit_exhausted, webhook_unsigned, webhook_rejected y los incidentes de salud (kommo_webhook_caido, kommo_token, ingesta_detenida, cola_atascada). **También notifica** el incidente de seguridad `registro_abierto` (`health-scan` lee `disable_signup` de `GET {SUPABASE_URL}/auth/v1/settings`, público, sin token de Management; está en el default de `webhook_kinds` y en las configs existentes por 0076). **No notifica:** `dream_error` (feedback de calidad, no una caída; varias por corrida; se revisa en `/dreams`) ni `media_processing_failed` (propia de SuperCines: es por mensaje y puede repetirse muchas veces al día; queda en `/alerts`).

Como no existían, nadie pudo haberlos quitado; la selección del operador sobre el resto se conserva. **SuperCines:** su producción es anterior y su `alert_config.webhook_kinds` es el default viejo de 4 tipos (`draft_failed`, `human_review_needed`, `outcomes_regression`, `inbound_silence`), así que `0081_supercines_alert_kinds_existing_config` suma además `inbound_dropped`, `kommo_webhook_disabled`, `budget_exceeded` y los 4 incidentes de salud (todos nuevos ahí; los 4 que ya tenía no se tocan). `supabase/tests/supercines_table_scopes.sql` verifica que esa config real queda con los 17 tipos. (No hay UI para editar `webhook_kinds`: hoy solo cambia por SQL.) Un tipo nuevo en el futuro: registrarlo en `ALERT_KINDS`, actualizar el default en una migración nueva (y apuntar a ella el test del default, que hoy lee 0076) y sumarlo a las configs existentes en esa misma migración.

**Anti-inundación (alertas que dispara un tercero sin autenticar).** Cada tipo del registro lleva `severity` (`critical`/`warning`/`info`). (1) *Prioridad:* `claim_alerts_for_webhook` atiende primero los tipos `critical` (p. ej. kommo_webhook_disabled, provider_credit_exhausted, budget_exceeded, salesbot_not_delivered, inbound_dropped): nunca esperan detrás de warnings o infos; los NO críticos tienen además un tope de 3 por tipo y barrido (el cupo total sigue siendo 10). (2) *Agregación en el INSERT:* los tipos de alta frecuencia y origen externo (`webhook_rejected` 1 h, `webhook_unsigned` 6 h, `inbound_dropped` 15 min; `aggregateMinutes` del registro) se guardan con `insert_alert_aggregated` (upsert por tipo + ventana): UNA fila por ventana con `agg_count` y el último detalle, así ni la tabla ni el webhook crecen con la inundación (1000 requests con token falso = 1 fila, 1 aviso). `insertAlert` lo usa solo y, sin la 0076 (PGRST202), inserta una fila normal. (3) *Rate limit en el origen:* el webhook público solo puede producir una fila por tipo y ventana (`kommo_webhook_note`).

### Techo de gasto mensual (`MONTHLY_BUDGET_USD`)

Segunda red de seguridad, independiente de los frenos por lead (cooldown / máx. respuestas): corta un gasto AGREGADO disparado (ráfaga de leads, cambio de modelo/precio, un bug). Ausente o `0` en `runtime_config.MONTHLY_BUDGET_USD` = **sin freno** (default; no cambia ningún despliegue existente). Se edita desde `/consumo` → "Techo de gasto mensual" (`/api/usage/budget`, alcance **configuracion** en `lib/auth/roles.ts`, igual que `/api/usage/models`; la UI deshabilita el control sin ese alcance). Claves: `MONTHLY_BUDGET_USD`, `BUDGET_SAFETY_MARGIN_PCT` (0..50, default 0) y `BUDGET_EXCLUDE_BEFORE` (activar a mitad de mes sin contar lo ya gastado).

- **Es una ESTIMACIÓN**: el gasto = `gasto_mes_actual()` (migración 0060) = suma de `usage_events.estimated_cost_usd` del mes UTC. Las sesiones CMA se valúan a tarifa base y con el modelo REAL de la sesión (`agent.model` del GET de sesión, no `AGENT_MODEL`): es cota inferior si una request interna supera 100K tokens. El margen de seguridad adelanta los cortes para compensarlo.
- **La ingesta NUNCA se frena** (leads, mensajes, etapas, pipelines: el inbox sigue vivo y `health-scan` no ve un falso "ingesta detenida"); solo se frenan las llamadas al modelo:
  - **≥100%**: `generate-response` y `follow-up-scan` no reclaman nada (los mensajes se responden al reanudar; `force_review` desde el inbox no se bloquea), y `evaluate-outcomes` (graders LLM) y `dreams-run` se omiten (se reintentan solos).
  - **≥110%**: `process-inbound` guarda el mensaje pero omite el clasificador y lo marca `classification.error = "budget: …"` (sin prefijo `recover:`); `recoverFailedClassifications` lo reclasifica solo al reanudar (y no reclasifica mientras el gate esté cerrado). `answer_max_age_hours` evita contestar mensajes viejos. Vencida la ventana de recuperación sin poder clasificar, el mensaje pasa a revisión humana (`recover:`), pero SOLO si venció hace menos de `RECOVER_EXPIRE_GRACE_DAYS` (3 días, `_shared/classify-recovery.ts`): el histórico más viejo se ignora sin tocarlo; la alerta agregada es una por 6 h (se le suma el conteo mientras no se reconozca).
- `_shared/budget.ts`: cache 60s (se invalida al cambiar techo, margen o `BUDGET_EXCLUDE_BEFORE`) y **fail-open absoluto**. El aviso lo emite `alerts-scan` (`budget_exceeded`, una alerta ABIERTA por mes y nivel, con webhook) y **se resuelve sola** al cambiar de mes, subir/quitar el techo o bajar el gasto.

### Agente vivo desactualizado (scaffold / modelo)

`syncAgentTools` guarda `runtime_config.AGENT_SCAFFOLD_HASH` (huella del `CORE_SCAFFOLD`) al empujar el system prompt. Si el código se actualiza y la huella no coincide, o si el modelo vivo en Anthropic difiere de `AGENT_MODEL`, Ajustes → Agente (`/settings`) y `/consumo` muestran un banner con botón **Sincronizar** (`POST /api/agent/sync`, alcance configuracion; no toca `SYSTEM_PROMPT`). **No se sincroniza solo** a propósito: un sync sube la versión del agente en producción y dispararlo desde el render de una página GET sería un efecto secundario concurrente y no decidido por nadie. `/consumo` también muestra el modelo vivo junto al selector.

### Modelos: Haiku 5.5, thinking, effort y refusals

Todo el LLM del template corre en **Haiku 5.5** (`claude-haiku-5-5`) por defecto; cada componente es intercambiable desde `/consumo`. Defaults en **dos** lugares que deben coincidir: `web/src/lib/model-config.ts` (`MODEL_KEYS`) y `supabase/functions/_shared/models.ts` (`MODEL_DEFAULTS`) — `supabase/tests/web-parity.test.ts` lo verifica. Agregar un modelo = `ALLOWED_MODELS` + `MODEL_LABELS` + `MODEL_NAMES` + fila en `AI_PRICING` (ambas copias).

- **Precio escalonado** (`ai-pricing.ts`, DOS copias idénticas — `supabase/tests/web-parity.test.ts` verifica paridad): Haiku 5.5 = $0.10/$0.50 por MTok (cache read $0.01, write 5m $0.125, 1h $0.20) si el prompt de la request es ≤100K tokens; si lo supera, **toda** la request paga $0.50/$2.50 (read $0.05, write $0.625/$1.00). El largo del prompt cuenta input + cache read + cache write. Las filas de sesión CMA son agregados de varias requests → se marcan `aggregated: true` y se valúan a tarifa base (cota inferior). Tokenizer nuevo: ~30% más tokens que Haiku 4.5 para el mismo texto.
- **Adaptive thinking viene ACTIVO** y cuenta contra `max_tokens`. Nunca leer `content[0]`: `_shared/llm.ts` (`textOf`/`jsonOf`) toma el bloque de texto y tira errores tipados ante `stop_reason: "refusal"` (`LlmRefusalError`), `"max_tokens"` (`LlmTruncatedError`) o ausencia de texto (`LlmEmptyError`). Cada call site usa un perfil de `LLM_PROFILES` (effort explícito + `max_tokens` con holgura): classify=low/4096, grader=medium/4096, comment_reply=low/2048, dreams learnings=medium/16000, digest=low/8000. El `effort` se arma SIEMPRE con `effortFor(model, …)` (`_shared/models.ts`): Haiku 4.5 (histórico, aún asignable) lo rechaza con 400, así que no se envía. Las llamadas fallidas (refusal/corte) igual se registran en `usage_events` (`recordFailedLlmUsage`) para que el techo de gasto no las subestime. No enviar `temperature`/`top_p`/`top_k`/`budget_tokens` (400 en Haiku 5.5); no hay `fallbacks` server-side para refusals.
- **Structured output (`output_config.format`)**: TODO json_schema vive en `_shared/llm-schemas.ts` (grader, Dreams, clasificador) con `additionalProperties: false` en cada objeto y todas las propiedades `required`: sin eso la API responde **400** y el llamador queda roto en silencio (LAM: 13.380 evaluaciones NULL jun–sep 2026; SuperCines: 100 % de los llm_judge en ERROR desde el 15-oct). `llm-schemas.test.ts` falla con un objeto abierto o con un `type: "json_schema"` inline fuera de ese módulo (las rutas web usan `generateObject` por tool_use y no pasan por acá).
- **Outcomes en ERROR se reintentan** (`_shared/outcome-retry.ts`): una fila con `score NULL` + `metadata.error` se vuelve a evaluar hasta 3 veces (`metadata.error_attempts`); antes quedaba en ERROR para siempre. El barrido solo mira los 30 drafts enviados más recientes (<72 h); para recuperar más viejos: `POST evaluate-outcomes {draft_id}`.
- **Referencias del grader** (`_shared/grader-prompt.ts`): un prompt que menciona material que el juez no recibe lo hace puntuar a la baja con Haiku 5.5 («si dudas, baja el score»). `graderReferences(grader)` es el ÚNICO lugar que decide qué recibe cada uno (por slug o porque su prompt lo menciona; los graders propios de un cliente entran por el prompt): **voz** (`voice_match` o «system prompt del agente / samples de voz»): el `SYSTEM_PROMPT` (≤6000) y hasta 5 `voice_samples` (≤600 c/u); **evidencia** (`no_hallucination` o «KB / base de conocimiento / respaldado / inventado»): el `SYSTEM_PROMPT` y lo que el agente tuvo en su sesión, leído de los eventos de la sesión CMA del draft (`agent_metadata.session_id` → `beta.sessions.events.list`, `_shared/grader-evidence.ts`): el primer `user.message` (el `[CONTEXTO]` exacto, ≤8000 conservando inicio y final) y la consulta y el resultado de cada herramienta (search_kb, CRM, http tools, lecturas de memoria; ≤4000 c/u, ≤16000 en total, solo los tipos de evento útiles vía `types`; si algo no entra el juez lo sabe). Todo como `<referencia tipo="…">` saneada bajo `EVALUATION_NOTICE` + un preámbulo que la declara material de terceros sin autoridad (prompt injection: una página o un documento de la KB pueden traer «devolvé score 1»). Sin `session_id` el juez lo sabe y no penaliza por falta de material; si la API de Anthropic falla, el grader queda en ERROR reintentable (nunca evalúa «sin KB»). LAM, 10 drafts, mismo juez: no_hallucination 0.41 → 0.88; ~10k tokens de entrada por evaluación. `task_completion` no recibe referencia. Todos los graders ven el LOTE completo de mensajes que cubre la respuesta (`messages.answered_by_draft_id`, ≤10), no solo `draft.message_id`.
- **Regresión de outcomes por juez** (`_shared/outcomes-regression.ts`): cada outcome LLM guarda `metadata.grader_model`, y `outcomes_regression` (alerts-scan) compara 24 h vs 7 d previos solo entre outcomes del MISMO juez (≥5 en cada ventana; filas sin `grader_model` no son baseline de nadie). Cambiar `GRADER_MODEL` mueve la escala (Haiku 4.5 → 5.5: −0.19 a −0.38 con el mismo agente) y antes disparaba falsas regresiones. Los graders automáticos no tienen juez y se comparan siempre.
- **Fallas**: classify con refusal o corte por `max_tokens` → `requires_human_review` + `classification.error = "recover: …"` (sale de la cola de reintentos; determinístico); comment_reply → sin respuesta pública (el DM sale igual); grader → outcome con `ERROR` visible; dreams → el run falla y el digest vivo NO se pisa.
- **Managed Agent**: `model` se envía como objeto `{id, effort}` (`web/src/lib/model-capabilities.ts`, `AGENT_EFFORT="medium"`), tanto al crear (`/api/setup/agent`) como al cambiar de modelo (`/api/usage/models`, que compara contra el agente VIVO, no contra `runtime_config`). Haiku 4.5 (histórico) no admite effort → string plano.
- **Rutas AI SDK del dashboard** (`lib/dashboard-ai.ts` + `lib/model-capabilities.ts`): corren `ai@5` (pin exacto 5.0.267 + `@ai-sdk/anthropic` 2.0.106, que NO conoce `claude-haiku-5-5`). Un único punto, `dashboardModel(apiKey, DASHBOARD_TASKS.<ruta>)`, fija por ruta el `effort` (nativo: `providerOptions.anthropic.effort` → `output_config.effort`, solo si `capsFor(modelo).effort`; Haiku 4.5 lo rechaza) y el `maxOutputTokens` (vía `defaultSettingsMiddleware`: sin él el provider manda `max_tokens=128000` para un modelo desconocido). Ninguna ruta envía `temperature`/`top_p`/`top_k`. `MODEL_CAPS` está duplicada en `_shared/models.ts` (paridad testeada). `generateObject` fuerza tool_choice (Haiku 5.5 lo acepta y no emite thinking). Un refusal llega como `finishReason: "content-filter"` (`aiErrorMessage` cubre también `"unknown"`). Una ruta nueva DEBE agregar su tarea a `DASHBOARD_TASKS` (el test `dashboard-ai-body.test.ts` afirma `max_tokens` acotado y effort por cada una). Ese test importa el `dashboardModel` real; sus imports bare salen del `deno.json` de la raíz (pins verificados contra `web/package.json`).

### Memoria y aprendizaje (Anthropic Managed Agents)

- Dos Memory Stores montados como filesystem en la sesión CMA. Sus nombres reales se configuran vía env vars (`MEMORY_STORE_MASTER_NAME` / `MEMORY_STORE_LEADS_NAME`):
  - **master** (read-only, global a todos los leads): `/voice/` (voz), `/kb/` (KB destilada), `/dreams/` (aprendizajes).
  - **leads** (read-write, por lead): solo `/<lead_id>/learnings.md` (datos duraderos del lead; el agente lo escribe únicamente si aprendió algo nuevo). **`conversation.md` ya NO se lee ni se escribe**: el historial viaja en el `[CONTEXTO]` (ver abajo). Los `conversation.md` de leads viejos quedan huérfanos e inocuos. **Al desplegar esto en un cliente existente**: (1) botón **Sincronizar** del banner en `/agent` o `/consumo` (o volver a guardar `/agent`) para que `syncAgentTools` suba el scaffold nuevo a Anthropic — hasta entonces el agente vivo sigue con el viejo, que contradice las `instructions` de sesión; (2) las `description` de los Memory Stores solo se escriben al crearlos: en stores ya creados conservan el texto viejo (cosmético; mandan las `instructions` por sesión); (3) si el `SYSTEM_PROMPT` del cliente tiene sus propios pasos de leer/escribir `conversation.md` o leer `/dreams/`, retirarlos.
- En el código (web + edge) usamos los labels semánticos `"master"` y `"leads"` para no acoplar el schema a un nombre específico de store. El ID real viene de `ANTHROPIC_MEMORY_MASTER_ID` / `_LEADS_ID`.
- **Historial determinístico de la conversación** (`supabase/functions/_shared/history.ts`): el contexto conversacional NO depende de que el modelo escriba/lea `conversation.md` (un tool call que el CMA podía omitir → respuestas sin contexto, y el mayor costo de tokens por respuesta). `fetchLeadHistory` reconstruye el transcript real Lead/Agente desde `messages` + `drafts` (join `drafts!messages_answered_by_draft_id_fkey`, mismo patrón que `dreams-run`; solo cuenta drafts `sent`/`auto_sent`). `generate-response` lo inyecta como bloque `[HISTORIAL]` (~24 turnos) antes de los mensajes nuevos; `process-inbound` le pasa al clasificador los últimos ~6 turnos para desambiguar (`"sí, dale"`, `"y cuánto?"`). `fail-soft`: ante error devuelve `""` y cae al comportamiento previo. Es la ÚNICA fuente del historial: `agent-prompt.ts` (CORE_SCAFFOLD), las `instructions` de los Memory Stores (`_shared/memory-instructions.ts`, compartidas por `generate-response` y `follow-up-scan`) y `agent/system-prompt.example.md` ya no piden leer/reescribir `conversation.md` ni leer `/dreams/`. `learnings.md` queda para datos duraderos. Dreams (daily y weekly) arma su insumo desde `messages` + `drafts` (la historia determinística de la DB), así que dejar de volcar a `conversation.md` no le quita materia prima. Tocar esas instrucciones sin mantener la coherencia con el `[CONTEXTO]` reintroduce el costo: `memory-instructions.test.ts` lo vigila.
- **Dreams**: `dreams-run` analiza conversaciones (24h/7d), DREAMS_MODEL (Haiku 5.5) destila learnings y los escribe como `.md` en `<master>/dreams/`. **El agente ya NO lee `/dreams/` por filesystem** (con muchos archivos activos eso costaba listado + lecturas + turnos extra en CADA respuesta): tras cada corrida, `dreams-run` consolida los dreams en el digest que ve el agente (`rebuildDigest`, `runtime_config.DREAMS_DIGEST`, tope `DREAMS_DIGEST_MAX_WORDS` 300–3000, default 900). **Dos piezas de estado, a propósito**: `DREAMS_ARCHIVE_DIGEST` (esencia de lo ya archivado — lo ÚNICO que «rueda» entre corridas) y `DREAMS_DIGEST` = consolidación de (resumen archivado + dreams ACTIVOS de ahora), que NUNCA se realimenta con el digest anterior (`_shared/dreams-consolidation.ts` no recibe un digest previo: **borrar un dream lo saca del digest en el siguiente rebuild por construcción**; antes su regla seguía viva dentro del digest anterior). El archivado consolida la esencia ANTES de borrar nada. «Gana la última en empezar» (`DREAMS_DIGEST_RUN`): un rebuild lento no pisa a uno más nuevo. `digest_only` y el rebuild de las corridas del cron van en `EdgeRuntime.waitUntil` (202) (la llamada al modelo se **omite si nada cambió**: `runtime_config.DREAMS_DIGEST_FINGERPRINT` guarda un hash del set de dreams activos post-archivado + el resumen archivado + el digest vigente + modelo + `DIGEST_PROMPT_VERSION` + tope de palabras; `_shared/dreams-digest-fingerprint.ts`. Cualquier aprobar/borrar/importar/editar cambia el hash y el `digest_only` reconstruye; el fingerprint y el digest previo se leen FRESCOS de la DB, no del cache de 60s; si cambiás el prompt de consolidación, subí `DIGEST_PROMPT_VERSION`; con exceso sobre `DREAMS_MAX_ACTIVE` nunca se omite porque el archivado va por tandas), y `generate-response` lo inyecta al contexto de cada sesión como bloque `aprendizajes_del_operador` (**prioridad mayor que la voz base**, TTL 60s, sin re-sync). Las mutaciones del dashboard (aprobar/borrar/importar) disparan `dreams-run {digest_only:true}` fire-and-forget (`triggerDigestRebuild`, `lib/memory-list.ts`) para que el cambio llegue al agente en <60s. Cota de activos: `DREAMS_MAX_ACTIVE` (default 60) — el exceso más viejo se archiva a `/dreams-archive/` (fuera del dashboard y de futuras consolidaciones; su esencia persiste en `DREAMS_ARCHIVE_DIGEST`, en tandas de `ARCHIVE_BATCH=50` por corrida para no exceder los recursos del worker). Cada learning lleva `severity` (sugerencia|advertencia|error, codificada también en el filename como `sug|adv|err`) y la política `runtime_config.DREAMS_AUTO_ACTIVATE` decide qué se activa solo: `all` (default), `error` (solo errores se auto-activan = autocorrección; el resto espera aprobación) o `none`. Lo no activado va a `/dreams-pending/` (no entra al digest) y se aprueba/descarta desde `/dreams`. Todo dream `error` genera una alerta (`kind=dream_error`). Borrar un activo lo saca del digest en el próximo rebuild (<60s). **Los aprendizajes no son una fuente de datos** (`_shared/dreams-digest-block.ts`): Dreams aprende de lo que DIJO el agente, así que un dato que el agente repite mal (KIA: «Soluto automático $25.500», de una KB vieja ya retirada) se «confirmaba» por repetición, entraba al digest con prioridad máxima y el agente lo seguía dando: un error que se realimenta. `LEARNINGS_DATA_RULE` (generación y consolidación) prohíbe fijar una cifra respaldada solo por lo que dijo el agente, y `dreamsDigestBlock` (único armado del bloque en generate-response y follow-up-scan) le aclara al agente que precios, montos y versiones salen solo de sus fuentes oficiales. Test: `dreams-digest-block.test.ts`.
- **Audio (notas de voz)**: si `respond_to_audio=true` y hay `OPENAI_API_KEY` en `runtime_config`, `process-inbound` transcribe con Whisper (`whisper-1`) y el texto sigue el pipeline normal (se guarda como `🎙️ <transcript>`). Sin key → `media_audio_no_key`; transcripción fallida → `requires_human_review`. La key se pide al activar el toggle en `/agent` → Filtros → Multimedia.
- `search_kb` es un custom tool del agente: embeddings gte-small 384d (`embed` function) + RPC `search_kb` (vector 0.7 + FTS español 0.3).
- Captura de mensajes salientes manuales de Kommo: **no resuelto**. El webhook `leads.add` no trae texto; los mensajes tecleados a mano viven en el sistema de chat de Kommo (amojo, credenciales aparte). Lo único recuperable vía API es lo que pasa por el custom field configurado (eventos `/api/v4/events`).

### Front (Next.js App Router)

- **Resilient boot**: el middleware (`src/middleware.ts` → `lib/supabase/middleware.ts`) detecta la ausencia de env vars de Supabase y redirige todo (excepto `/first-run/**`, `/api/provision/**`, `/_next/**`, `/favicon.ico`) al wizard de configuracion inicial. Nunca lanza un 500 aunque el entorno esté vacío.
- **`/api/provision/*` NO es pública para siempre** (`lib/provision/gate-logic.ts` + `gate.ts`). El middleware la deja pasar sin sesión solo porque el `/first-run` corre antes de que exista un usuario. Cada ruta decide: el `ref` es SIEMPRE el de `NEXT_PUBLIC_SUPABASE_URL` (un `ref` en el body se ignora); `migrate` y `functions/deploy` corren sin sesión SOLO mientras el proyecto no tiene ningún usuario (primer arranque, contado con la Admin API; si no se puede contar → 503) y únicamente con el token `sbp_` que manda el body; con algún usuario exigen sesión `configuracion` (`requireScope`) y recién ahí pueden usar el token guardado en `runtime_config`. `updates` exige sesión `configuracion` siempre; `status` (pública) no usa el token: lee `_migrations` y `DEPLOYED_FUNCTION_HASHES` con la service-role, y con un usuario creado ya no vuelve a «initialize». ### Quién entra y hasta dónde (gestión de usuarios)

`/usuarios` (alcance `configuracion`) administra quién tiene acceso al panel: crear,
cambiar el alcance, resetear la contraseña y borrar. Se apoya en la Admin API de Supabase
Auth con la service-role key (`web/src/lib/users/admin.ts`, server-only).

**El alcance vive en `app_metadata.role`** de Supabase Auth, que sólo se escribe con
service-role: viaja firmado en el JWT y se lee sin round-trip a la base.

**Tres alcances acumulativos** (`web/src/lib/auth/roles.ts`, el único lugar donde se decide):

| Alcance | Ve | Para quién |
|---|---|---|
| `operacion` | Inbox, Leads, Alertas | Quien atiende conversaciones |
| `contenido` | + Contenido, Promos, Verticales, Outcomes, Consumo, Dreams | Quien edita qué dice el agente |
| `configuracion` | + Agente, Kommo, Herramientas, Seguimiento, Ajustes, Usuarios | Quien toca credenciales y el encendido |

`admin` y `editor` siguen leyéndose como alias (`admin`→`configuracion`, `editor`→`contenido`),
así que adoptar este módulo no le cambia el acceso a ningún usuario existente. Ya no se escriben.

- **El gate está en el MIDDLEWARE, y vale para páginas Y para `/api/*`.** Ocultar un ítem del
  menú no es un permiso: la ruta se sigue alcanzando escribiendo la URL. `nav.tsx` OCULTA,
  el middleware PROHÍBE, y cada ruta sensible vuelve a comprobar por su cuenta.
- **UN VALOR DESCONOCIDO CAE CERRADO.** La versión vieja hacía
  `r === "editor" ? "editor" : "admin"`: cualquier cosa que no fuera exactamente `"editor"`
  —un typo, `"Editor"`, un dato corrupto— **regalaba acceso total**. Ahora un valor presente
  pero un valor irreconocible cae CERRADO (sin acceso), igual que en SQL.
- **SIN ROL = SIN ACCESO** (`SIN_ACCESO` en `roles.ts`). Antes la AUSENCIA de rol abría todo
  («es el maestro del first-run»); con el registro público de Supabase Auth encendido (default de
  un proyecto nuevo) cualquiera con la anon key hacía `signUp` y entraba como administrador.
  Ahora un usuario sin rol (ausente, `null` o `""`) solo ve `/sin-acceso` (aviso + cerrar
  sesión) y `/auth/*`; toda ruta de API le responde 403, incluso las que no tienen alcance
  declarado. Se eligió «sin acceso» y no `operacion` porque `operacion` igual expone leads y
  conversaciones (PII) a alguien que nadie dio de alta. Lo legítimo siempre tiene rol: el
  `/first-run` crea al maestro con `configuracion` explícito y `/usuarios` rechaza crear sin
  alcance (400). `/usuarios` muestra «Sin acceso» para asignarles uno. **Orden de deploy:** la
  migración 0078 (al empezar asigna `configuracion` SOLO al usuario MAESTRO —el creado primero,

  `/usuarios` avisa) va ANTES que esta web. **En SuperCines todos los usuarios de producción ya tienen rol explícito** (asignado antes de este deploy); en otro entorno, asigná rol explícito a los demás
  usuarios legítimos existentes y revisá `auth.users` (borrá lo que no reconozcas). Como las migraciones se aplican desde el panel, si la web llega primero hay

### Secretos y runtime_config (migración 0079, `lib/config-secrets.ts`, `lib/auth/require-scope.ts`)

- **`runtime_config` solo por el servidor.** `authenticated`/`anon` sin privilegio ni policy. El
  panel lee con `lib/runtime-config.ts` (cliente de servicio) DESPUÉS de validar sesión + alcance:
  rutas con `requireScope(scope)` (401/403), páginas con `requirePageScope(scope)` (→ `/login` o
  `/inbox`). El alcance que pasa cada una debe coincidir con `PATH_SCOPES` (lo verifica un test).
- **Escribir exige un `ConfigWriter`** (`{ by, scope }`), que solo fabrica `requireScope`;
  `setConfigValues` valida clave por clave (`configKeysDenied`): `configuracion` todo,
  `contenido` solo `DREAMS_AUTO_ACTIVATE`/`DREAMS_FREQUENCY`, `operacion` nada.
  `syncAgentTools`/`renameAgent` reciben el mismo writer.
- **Clasificación única de secretos**: `lib/config-secrets.ts` mantiene la lista de lo PÚBLICO
  (`PUBLIC_CONFIG_KEYS` + `TOOL_<X>_HOSTS`); **clave desconocida ⇒ secreta**. La columna
  `runtime_config.is_secret` (0017) es informativa y no decide nada.
- **Un secreto nunca viaja al navegador** (ni a `configuracion`): se muestra `maskSecret` →
  `••••1234` (últimos 4, solo si tiene ≥16 caracteres; si no `••••`) y se REEMPLAZA (input vacío =
  conservar, `secretInputAction`). Así se ven la API key de Anthropic y el token de Kommo en el
  drawer de setup (`setupStateFromConfig`, puro), la key de OpenAI en `/agent` → Multimedia y el
  webhook de alertas en `/settings` (con «Quitar el webhook»). `kommo_credentials` y `alert_config`
  se leen con service_role en `/config/kommo` y `/settings`.
- **Pares destino + secreto** (`lib/secret-bound-config.ts`, una sola regla para todos): un secreto queda atado al destino con el que se cargó. Si una escritura AGREGA un destino (host nuevo; cambiar solo la ruta del mismo host no cuenta), cada secreto del par que siga vigente tiene que venir con un valor NUEVO en esa misma escritura (o borrarse; si el secreto viene del entorno, borrarlo en la base no alcanza). Pares: `BCV_RATE_URL` → `BCV_RATE_APIKEY` (por origin); `KOMMO_API_DOMAIN` → `KOMMO_ACCESS_TOKEN`; `SHOPIFY_STORE_DOMAIN` → `SHOPIFY_ACCESS_TOKEN`/`SHOPIFY_CLIENT_ID`/`SHOPIFY_CLIENT_SECRET`; `TOOL_<X>_HOSTS` → `TOOL_<X>` (agregar un host). Lo aplica `setConfigValues` en TODA escritura (lee los valores vigentes en el momento; `SecretBindingError` → la ruta responde 400). Sin par (destino fijo o la URL ES el secreto): Anthropic y OpenAI (hosts fijos en código), webhook de alertas (`alert_config.webhook_url`, secreto en sí). `/api/setup/kommo` exige un `api_domain` atable (`normalizeHost`) y `/api/agent/bcv` valida `BCV_RATE_URL` con `parseToolUrl(strict)` y guarda la href normalizada; el fetch de la tasa con key (web y edge) usa esa misma validación y `redirect: "manual"`. La UI de BCV avisa que la key se quita si no se vuelve a pegar al cambiar la URL.
- **Guardia de código** (`lib/config-access.test.ts`): `.from("runtime_config")` solo en
  `lib/runtime-config.ts` y los módulos de provisión (cliente con service-role); ningún componente
  `"use client"` importa un lib que lea secretos; toda ruta/página que importe uno llama a

  escribe config lo hace con `auth.writer`. `config-secrets.test.ts` cubre clasificación,

### Body de las rutas de API: lectura única (`lib/api/body.ts`)

**Ninguna ruta lee el body a mano** (`request.json()`, `request.formData()`, `request.text()`,
`request.body`…): todas usan `readJson(request, schema, { optional? })` o
`readForm(request, schema, { maxBytes? })`, que devuelven `{ ok: true, data }` (tipado por el
schema zod de la ruta) o `{ ok: false, response }`. **Body inválido = 400** (`code: "invalid_body"`),
nunca 500: JSON roto, cuerpo vacío (salvo `optional`, que valida `{}`), UTF-8 inválido, body que no
es objeto, tipos equivocados, multipart roto y content-type que no corresponde (una ruta JSON exige
- **PostgREST corta cada respuesta en `max_rows` (1000) SIN error ni aviso.** Todo select que pueda pasar de 1000 filas (corpus de Dreams, regresión de outcomes, cualquier ventana de tiempo) se lee con `collectKeyset` (`_shared/keyset-pages.ts`): keyset por `(created_at, id)` (nunca OFFSET), tope duro con `truncated` y error de página = excepción. El listado de Memory Stores pagina con `page`/`next_page` (`web/src/lib/memory-pages.ts`); `after_id`/`has_more` no existen en esa API.
`application/json` o `+json`; una de formulario acepta `x-www-form-urlencoded` y `multipart/form-data`;
ninguna acepta ambos). **Tamaño**: 1 MB por defecto (`MAX_BODY_BYTES`), cortado al leer el stream (no
se confía en Content-Length) → **413** `body_too_large`; las subidas de KB y voz usan
`MAX_UPLOAD_BODY_BYTES` y `uploadFile` (archivo ≤ 5 MB, lo que promete la UI). El mensaje es el
primer error de zod en español **sin el valor recibido** (`describeIssue`: los mensajes por defecto
de zod sí lo incluyen, p. ej. en un enum; el body puede traer secretos). `readForm` entrega el
PRIMER valor de cada campo (misma semántica que `form.get`). Orden en cada handler: autorizar
(`requireScope`/`getUser`/`authorizeProvision`, 401/403) → leer el body → resto; la única ruta que
lee body sin sesión es `provision/register` (primer usuario). El helper no importa nada de servidor,
así que sirve en `api/provision/**`. Una validación que ya vive en un lib con tests
(`parseRetryBody`, `validateCreate`/`validatePatch`, `parseExpected`) se mantiene: el schema
garantiza la forma y el lib los mensajes de negocio. Tests: `lib/api-body.test.ts` (tabla de bodies
inválidos/válidos), `lib/api-body-guard.test.ts` (guardia AST: ningún `route.ts` lee el body del
request fuera del helper y todos autorizan antes de leerlo) y `lib/api-body-routes.test.ts`
(importa CADA ruta con stubs de Next/sesión/base vía `module.registerHooks` y le manda bodies
inválidos: 400/413, y sin sesión 401; si una ruta toca la base o la red con un body inválido, falla).

## Convenciones y gotchas

- **`runtime_config` es la single source of truth** para credenciales e identidad por cliente (migración 0017/0018). Web y Edge leen DB-first/env-fallback; ya NO hace falta publicar secrets de Anthropic/Kommo vía Management API ni mantener los mismos valores en `web/.env.local` y en secrets de Supabase — el wizard `/first-run` + `/setup` los escribe una vez en DB. Lo único irreducible en el host como env vars: los 3 secretos de arranque de Supabase (URL, anon, service-role) que se necesitan para leer la DB. **Postura de seguridad (0079)**: las credenciales viven en texto plano, pero solo las lee `service_role`/el dueño (ni `authenticated` ni `anon` tienen acceso) y nunca viajan al navegador (ver «Secretos y runtime_config»). El cifrado pgcrypto sigue diferido a propósito: con la clave en la misma base, quien puede leer la tabla (service_role/dueño) también puede leer la clave, así que el cifrado en reposo no agrega separación real. Se reconsidera si aparece un requisito de compliance o un KMS externo que guarde la clave fuera de la base.

- UI en español, light theme. ### 0. Pre-vuelo (solo lectura; si algo falla, NO seguir)

1. **Qué hay aplicado de verdad** (la lista de pendientes sale de acá, no de memoria):
   `select filename from _migrations order by filename;` y restar lo ya registrado. Todas las migraciones **≥ 0060 son idempotentes** (el test
   `verify:sql` las aplica dos veces): si alguna de las que siguen ya estaba aplicada, volver a correrla es inocuo.
   Las **anteriores a 0060 NO** son re-ejecutables (0006 y 0053 cambian el tipo de retorno de una función).
   Producción NO tiene registradas `0057`, `0058_claim_inbound_batch_created_at` ni `0059` aunque sus efectos están
   presentes: **insertarlas en `_migrations`** antes de que alguien use `/api/provision/migrate`
   (`insert into _migrations(filename) values (...) on conflict do nothing;`), o el runner las re-ejecutaría.
2. **Todo usuario con rol válido** (con 0078/0079 «sin rol» = sin acceso):
   `select email, raw_app_meta_data->>'role' as rol from auth.users order by created_at;` → cada fila en
   `operacion|contenido|configuracion` (o los alias `admin|editor`). Un NULL/`""`/valor raro queda **afuera**. Borrar lo
   que no se reconozca. 0078 solo promueve al maestro (el primero creado) si no tuviera rol.
3. **`KOMMO_ACCESS_TOKEN`, `KOMMO_API_DOMAIN` (y `BCV_RATE_APIKEY`, `TOOL_*` si existen) deben estar en `runtime_config`**:
   `select key, (value is not null and value <> '') as cargado from runtime_config where key in ('KOMMO_ACCESS_TOKEN','BCV_RATE_APIKEY') or key like 'TOOL\_%';`.
   Además, toda tool http con `{{TOOL_X}}` en sus headers necesita su `TOOL_X_HOSTS` (hosts exactos, coma) en `runtime_config`, y
   `{{KOMMO_ACCESS_TOKEN}}` solo viaja al host de `KOMMO_API_DOMAIN`: cruzar
   `select name, headers from agent_tools where headers::text like '%{{%';` con
